# Code → Business Model

## 1. 目标

从现有系统源码中重建一套可用于产品改版的 **AS-IS 现状业务模型**。

最终应能回答：

- 系统有哪些核心业务对象？
- 对象之间是什么关系？
- 不同角色能做什么？
- 核心对象从产生到结束经历哪些状态？
- 什么条件会导致不同业务路径？
- 不同配置、角色、状态、类型下有哪些真实场景？
- 驳回、撤回、终止、延期、重提、跳过等特殊情况如何处理？
- 一个业务规则变化后会影响哪些流程和场景？
- 当前有哪些内容仍无法从源码确认？

---

## 2. 三条强制原则

### 2.1 产品语言优先

正文只描述：

> 谁，在什么条件下，对什么业务对象，做什么，系统发生什么变化。

技术信息只放“证据来源”。

推荐：
> 当申请处于“待审核”状态时，学院管理员可以执行审核。

不推荐：
> status=2 时调用 auditService。

如输出技术味过重，读取：
`references/产品语言表达规范.md`

### 2.2 不确定内容禁止猜

统一标记：

```text
【待确认】
```

并进入：
`13-待确认问题.md`

### 2.3 AS-IS 与 TO-BE 分开

本 Skill 只还原当前系统。

发现问题时只记录：

```text
【设计观察】
```

不要直接把现有业务改写成更合理的方案。

# 3. 核心分析顺序

严格按以下顺序：

```text
系统模块
→ 业务对象
→ 对象关系
→ 生命周期
→ 业务规则
→ 条件分支
→ 业务场景
→ 完整流程
→ 角色权限
→ 配置与异常
→ 页面映射
→ 覆盖检查
```

**不要从逐页面分析开始。**

页面是业务操作入口，不是业务模型本身。

---

# 4. 阶段一：系统模块地图

输出：

`01-系统模块地图.md`

先识别：

- 主要业务模块
- 主要用户角色
- 主要业务入口
- 配置模块
- 审核/审批/评审流程
- 自动处理
- 第三方系统
- 客户/学校差异
- 历史兼容逻辑

这里只建立“大地图”，不深入逐页面。

---

# 5. 阶段二：业务对象模型

输出：

`02-业务对象模型.md`

业务对象编号：

```text
BO-001
BO-002
...
```

每个核心对象至少说明：

| 项目 | 内容 |
|---|---|
| 对象编号 | BO-xxx |
| 对象名称 | |
| 业务定义 | |
| 上级对象 | |
| 下级对象 | |
| 相关对象 | |
| 主要状态 | |
| 主要操作 | |
| 相关角色 | |
| 可信度 | 明确 / 推测 / 待确认 |

必须区分：

- 主业务对象
- 配置对象
- 过程对象
- 结果对象
- 记录/日志

不要把数据库表、页面、接口直接当成业务对象。

判断困难时读取：
`references/业务模型识别指南.md`

---

# 6. 阶段三：生命周期

输出：

`03-生命周期.md`

对每个核心对象梳理：

| 当前状态 | 操作/事件 | 条件 | 角色 | 下一状态 | 后续影响 |
|---|---|---|---|---|---|

必须主动寻找：

- 正向状态变化
- 驳回/退回
- 撤回
- 重新提交
- 取消
- 终止
- 暂停/恢复
- 延期
- 重开
- 自动关闭
- 超时

不要擅自合并不同状态。

发现状态但无法解释时标记【待确认】。

---

# 7. 阶段四：业务规则与决策表

输出：

`04-业务规则与决策表.md`

业务规则编号：

```text
BR-001
BR-002
...
```

每条规则说明：

- 规则名称
- 适用对象
- 前置条件
- 业务结果
- 相关场景
- 证据来源
- 可信度

重点寻找会改变业务行为的条件：

```text
状态
角色
权限
类型
配置
时间
数量
范围
结果
```

多条件逻辑优先使用决策表：

| 条件 | 情况A | 情况B | 情况C |
|---|---|---|---|
| 是否专家评审 | 否 | 是 | 是 |
| 评审方式 | - | 普通 | 盲审 |
| 后续流程 | 进入下一阶段 | 普通评审 | 盲审 |

专项补漏时读取：
`references/业务分支与场景检查清单.md`

---

# 8. 阶段五：业务场景库

输出：

`05-业务场景库.md`

场景编号：

```text
SC-001
SC-002
...
```

一个场景至少包含：

```text
谁
+
什么业务对象
+
当前状态
+
前置条件
+
执行操作
+
业务结果
```

必须覆盖：

### 主流程
正常创建、提交、审核、评审、完成。

### 重要分支
不同类型、配置、处理方式。

### 异常
驳回、撤回、终止、延期、超时、重复提交、数据不完整。

### 角色差异
不同角色在同一对象上的操作差异。

### 配置差异
开启/关闭配置后流程变化。

不要机械做：

```text
角色 × 状态 × 类型 × 配置
```

只保留源码支持的真实可达场景。

---

# 9. 阶段六：完整业务流程

输出：

`06-完整业务流程.md`

跨页面、跨模块串起端到端业务。

每个关键节点说明：

```text
谁处理
处理什么对象
什么条件
处理后去哪
```

建议分别表达：

- 主流程
- 异常流程
- 特殊流程

不要把所有分支挤在一张图里。

---

# 10. 阶段七：角色与权限

输出：

`07-角色与权限.md`

至少说明：

| 角色 | 可以看什么 | 可以操作什么 | 数据范围 | 限制条件 |
|---|---|---|---|---|

权限至少从以下四个维度理解：

```text
角色
+
数据范围
+
对象状态
+
操作权限
```

例如：

> 学院管理员只能审核本学院、且处于“待学院审核”状态的数据。

---

# 11. 阶段八：配置模型

输出：

`08-配置模型.md`

只重点梳理会改变业务行为的配置：

| 配置 | 作用范围 | 可选值 | 默认值 | 业务影响 |
|---|---|---|---|---|

重点确认：

- 配置作用在哪一层
- 不同取值产生什么业务差异
- 默认值是什么
- 是否是某客户/学校特例

可能的作用范围：

```text
全局
业务类型
批次
组织
个人
客户/学校
```

---

# 12. 阶段九：异常与特殊流程

输出：

`09-异常与特殊流程.md`

主动寻找：

```text
驳回
退回
撤回
作废
取消
终止
暂停
恢复
延期
变更
重新提交
超时
自动关闭
强制处理
特殊审批
历史兼容
```

模板：

| 情况 | 触发条件 | 谁发起 | 原状态 | 后续状态 | 是否可恢复 |
|---|---|---|---|---|---|

---

# 13. 阶段十：页面与业务映射

业务模型完成后，再分析页面。

输出：

`10-页面与业务映射.md`

至少建立：

| 页面/功能 | 主要业务对象 | 流程阶段 | 支持场景 | 主要操作 |
|---|---|---|---|---|

页面只需要补充产品关心的信息：

- 页面用途
- 使用角色
- 查询条件
- 列表/表单/详情字段
- 主要操作
- 显示/隐藏条件
- 可编辑/不可编辑条件
- 操作后的状态变化

不要让页面分析反过来主导业务模型。

---

# 14. 业务规则证据表

输出：

`11-业务规则证据表.md`

| 规则编号 | 业务规则 | 证据来源 | 可信度 |
|---|---|---|---|

主文档不要大段复制代码。

证据只用于说明：

> 为什么可以确认这条业务规则。

---

# 15. 覆盖检查

输出：

`12-覆盖检查.md`

这是强制阶段。

反向检查：

- 已发现状态是否全部解释
- 已发现业务类型是否全部解释
- 已发现业务条件是否进入规则/决策表/场景
- 权限差异是否进入权限模型
- 改变流程的配置是否进入配置模型
- 主要页面是否找到所属业务对象和流程阶段
- 异常路径是否记录

最终至少给出：

| 类型 | 已发现 | 已解释 | 待确认 |
|---|---:|---:|---:|
| 业务对象 | | | |
| 状态 | | | |
| 业务类型 | | | |
| 业务分支 | | | |
| 权限差异 | | | |
| 配置项 | | | |
| 业务场景 | | | |
| 页面/功能 | | | |

没有完成覆盖检查，不要声称“业务已完整梳理”。

验收时读取：
`references/业务模型质量检查清单.md`

---

# 16. 待确认问题

输出：

`13-待确认问题.md`

编号：

# 18. 大型系统执行方式

不要一次性深入整个大型仓库。

推荐：

```text
第1轮：系统模块地图
第2轮：逐业务域梳理对象和生命周期
第3轮：补业务规则、分支、场景
第4轮：合并跨模块完整流程
第5轮：专项补权限、配置、异常
第6轮：覆盖检查
```

持续维护：

`_progress.md`

大型系统读取：
`references/大型系统分批分析指南.md`

# 19. Reference 使用规则

默认**不要一次读取全部 references**。

只在需要时读取：

| 情况 | Reference |
|---|---|
| 不知道哪些才是真正业务对象 | `业务模型识别指南.md` |
| 担心漏分支/异常场景 | `业务分支与场景检查清单.md` |
| 输出技术味太重 | `产品语言表达规范.md` |
| 一个模块分析完成需要验收 | `业务模型质量检查清单.md` |
| 系统很大需要分批 | `大型系统分批分析指南.md` |

`expected_outputs/` 只用于校准颗粒度，不要默认全部读取。

`scripts/` 只负责机械盘点，不负责判断业务含义。

# 20. 稳定编号

统一使用：

```text
BO-001   业务对象
BR-001   业务规则
DT-001   决策表
SC-001   业务场景
CFG-001  配置
EX-001   异常流程
TBC-001  待确认问题
```

分批分析时保持编号稳定。

---

# 21. 完成标准

输出不是越长越好。

真正完成的标准是产品经理可以回答：

1. 核心业务对象有哪些？
2. 每个核心对象的生命周期是什么？
3. 不同状态下能做什么？
4. 不同角色为什么看到不同内容？
5. 什么条件导致不同流程？
6. 配置变化影响哪些业务场景？
7. 驳回、撤回、延期、终止分别如何处理？
8. 一个规则变化会影响哪些对象、流程和场景？
9. 还有哪些内容无法从源码确认？

如果这些问题仍然无法回答，继续分析，不要通过增加文档篇幅掩盖业务缺口。
