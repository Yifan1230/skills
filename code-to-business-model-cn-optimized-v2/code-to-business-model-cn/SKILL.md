# Code → Business Model

## 1. 目标

本 Skill 的任务不是“把代码翻译成中文”，而是：

> **从代码事实中还原业务含义，再用产品经理能够直接理解、讨论和改版的语言建立 AS-IS 业务模型。**

最终产品经理不看源码，也应能回答：

- 系统到底在管理哪些业务对象？
- 每个对象在业务上是什么？
- 对象之间如何产生、关联和流转？
- 不同角色什么时候可以做什么？
- 哪些条件会导致不同业务路径？
- 驳回、撤回、停开、恢复、延期、终止等特殊情况如何处理？
- 哪些规则属于业务共性，哪些由配置产生差异？
- 一个规则变化会影响哪些业务场景？
- 哪些业务含义仍无法确认？

---

# 2. 最重要的原则：业务语义层与技术证据层彻底分离

输出必须分成两层。

## 2.1 业务语义层（默认给产品经理阅读）

只能使用业务语言，描述：

```text
业务目的
角色
业务对象
业务状态
业务动作
业务规则
业务结果
业务异常
业务场景
```

正文默认禁止出现：

- 数据库字段名；
- 表名；
- 类名、方法名、函数名；
- API/接口内部名称；
- 变量名；
- 状态数字、代码值；
- SQL表达式；
- `A=1`、`A<>B`、`0↔1` 这类代码条件；
- 纯实现算法；
- 技术日志表、临时表名称。

例如，不要写：

```text
ZT 0↔1 → SFXS=0 → copyForHbpk → doAzpy
```

而应写：

```text
教学任务可以被停开；停开后不再参与正常教学安排；
具备权限的用户可以恢复停开的任务。
```

## 2.2 技术证据层（仅用于核验）

技术名称只允许进入：

```text
11-业务规则证据表.md
或 evidence/ 目录
```

例如：

| 业务规则 | 技术证据 |
|---|---|
| 教学任务支持停开和恢复 | 某状态字段及停开处理逻辑 |
| 合班后共享排课结果 | 某合班处理方法 |

技术证据的作用只是：

> 证明业务结论从哪里来。

不得反过来决定业务正文的表达方式。

---

# 3. 禁止“半中文半代码”的伪业务模型

以下内容即使事实正确，也视为不合格：

```text
选起始周 → 30位周次串位移 → newzcbh → doAzpy
```

```text
强制删除 → TKLY=xxx → SFXS=0 → ZT 0↔1
```

```text
读取 T_XXX → 调用 XXXService → 写入 XXX_LOG
```

这些属于技术实现摘要，不是产品业务模型。

必须先翻译成：

```text
业务上发生了什么？
为什么需要这个能力？
谁会使用？
在什么条件下使用？
处理后业务状态如何变化？
异常时怎么办？
```

---

# 4. 每个功能必须先完成“业务翻译”

发现一段重要代码逻辑后，不要直接写进业务模型。

先内部回答以下 7 个问题：

1. 这个功能在业务上是为了什么？
2. 谁会使用它？
3. 它处理哪个业务对象？
4. 什么情况下才会发生？
5. 用户做了什么业务动作？
6. 系统在业务上产生什么结果？
7. 有哪些限制、异常、恢复或后续动作？

如果回答不了，标记【待确认】，不要用技术过程代替业务含义。

---

# 5. 核心分析顺序

严格按照：

```text
系统模块
→ 业务对象
→ 对象关系
→ 生命周期
→ 业务规则
→ 条件分支
→ 业务场景
→ 端到端流程
→ 角色权限
→ 配置与异常
→ 页面/功能映射
→ 覆盖检查
```

**不要从逐页面介绍开始，也不要以一张主流程图作为最终业务模型。**

---

# 6. 阶段一：系统业务地图

输出：

`01-系统业务地图.md`

只回答：

- 系统包含哪些主要业务域；
- 每个业务域解决什么业务问题；
- 主要用户是谁；
- 业务域之间大致如何衔接。

不要在这一层写技术模块名、包名或接口名。

---

# 7. 阶段二：业务对象模型

输出：

`02-业务对象模型.md`

业务对象编号：

```text
BO-001
BO-002
...
```

每个对象至少说明：

| 项目 | 内容 |
|---|---|
| 对象名称 | 业务人员能理解的名称 |
| 业务定义 | 它在业务上代表什么 |
| 如何产生 | 由谁、由什么业务产生 |
| 上级/下级对象 | 与哪些对象存在稳定关系 |
| 主要状态 | 用中文业务状态表达 |
| 主要操作 | 用户能对它做什么 |
| 责任角色 | 谁负责 |
| 待确认 | 尚无法从源码确认的业务含义 |

必须区分：

- 主业务对象；
- 配置对象；
- 过程对象；
- 结果对象；
- 仅作为记录/日志存在的技术对象。

不要因为代码里有一张表，就创造一个业务对象。

需要时读取：
`references/业务模型识别指南.md`

---

# 8. 阶段三：生命周期

输出：

`03-生命周期.md`

每个核心对象用业务状态表达：

| 当前业务状态 | 业务动作/事件 | 前置条件 | 角色 | 下一业务状态 | 业务后果 |
|---|---|---|---|---|---|

必须覆盖：

- 正常流转；
- 驳回/退回；
- 撤回；
- 重新提交；
- 停开/恢复；
- 取消/终止；
- 暂停/恢复；
- 延期；
- 自动关闭；
- 超时。

如果源码里只有状态数字，先找到其业务含义；找不到则写【待确认】，不要在正文写“状态=99”。

---

# 9. 阶段四：业务规则与决策表

输出：

`04-业务规则与决策表.md`

业务规则编号：

```text
BR-001
BR-002
...
```

每条规则必须写成业务判断：

```text
适用对象
业务条件
允许/禁止的行为
业务结果
例外
相关场景
```

例如：

> 教学任务完成最终锁定后，普通维护人员不能继续修改排课信息。

不要写：

> validateCanEdit=false 时禁止保存。

多条件规则使用产品可读决策表：

| 业务条件 | 情况A | 情况B |
|---|---|---|
| 是否需要专家评审 | 否 | 是 |
| 后续业务 | 进入下一阶段 | 进入专家评审 |

需要补漏时读取：
`references/业务分支与场景检查清单.md`

---

# 10. 阶段五：业务场景库

输出：

`05-业务场景库.md`

场景编号：

```text
SC-001
SC-002
...
```

每个场景至少包含：

```text
场景目的
角色
业务对象
当前状态
前置条件
业务动作
业务结果
后续处理
异常/替代路径
```

必须覆盖：

- 主流程；
- 重要业务分支；
- 角色差异；
- 配置差异；
- 异常和恢复；
- 高频特殊场景。

不要机械穷举理论组合，也不要用方法调用链代替业务场景。

---

# 11. 阶段六：端到端业务流程

输出：

`06-完整业务流程.md`

流程图中只允许出现：

```text
角色
业务动作
业务对象
业务状态
业务结果
```

禁止出现：

```text
方法名
字段名
表名
状态码
函数参数
SQL条件
```

错误：

```text
选择周次 → newzcbh → doAzpy → 写ZTTKAZPYJL
```

正确：

```text
选择需要整体调整的教学周
→ 系统计算受影响课程
→ 用户预览调整结果
→ 确认执行
→ 更新课程安排并保留调整记录
```

---

# 12. 阶段七：角色与权限

输出：

`07-角色与权限.md`

| 角色 | 业务责任 | 可处理对象 | 可执行动作 | 数据范围 | 限制条件 |
|---|---|---|---|---|---|

权限要翻译成业务含义：

> 学院管理员只能处理本学院、且处于待学院审核状态的数据。

不要写角色代码、权限代码或菜单权限编号。

---

# 13. 阶段八：配置模型

输出：

`08-配置模型.md`

只保留对业务有意义的配置：

| 配置名称 | 业务含义 | 作用范围 | 可选方式 | 默认行为 | 对流程的影响 |
|---|---|---|---|---|---|

不要把系统参数表原样抄成配置模型。

---

# 14. 阶段九：异常与特殊流程

输出：

`09-异常与特殊流程.md`

至少寻找：

- 驳回；
- 撤回；
- 停开/恢复；
- 作废；
- 终止；
- 延期；
- 强制处理；
- 超时；
- 特殊审批；
- 历史兼容。

每个特殊流程先解释：

> 为什么业务上需要它。

再解释怎么处理。

---

# 15. 页面与业务映射

输出：

`10-页面与业务映射.md`

页面分析只回答：

| 页面/功能 | 业务目的 | 主要角色 | 业务对象 | 所处阶段 | 主要业务动作 |
|---|---|---|---|---|---|

页面字段可以列中文业务字段，但不要把后端字段代码直接放进产品正文。

---

# 16. 技术证据表

输出：

`11-业务规则证据表.md`

这是技术信息的主要承载位置。

| 业务规则编号 | 产品业务结论 | 技术证据位置 | 可信度 |
|---|---|---|---|

如需保留更多技术细节，写到：

```text
evidence/
```

而不是业务正文。

---

# 17. 产品可读性自检

每个业务文档提交前强制检查：

### 17.1 不看源码能否理解？

如果不能，重新翻译。

### 17.2 是否出现技术符号污染？

正文出现以下内容时默认判为失败：

- 连续大写字段代码；
- `T_XXX` 类表名；
- `xxx()` 方法；
- 状态数字；
- `=`, `<>`, `↔` 用于表达代码值变化；
- 参数名；
- SQL条件；
- 内部接口编码。

除非它们明确位于“技术证据”章节。

### 17.3 是否只是代码调用链换成中文？

如果是，重新回答：

> 这段逻辑在业务上解决什么问题？

---

# 18. 覆盖检查

输出：

`12-覆盖检查.md`

检查：

- 业务对象；
- 中文业务状态；
- 业务类型；
- 规则分支；
- 角色权限；
- 业务配置；
- 异常路径；
- 业务场景；
- 页面/功能。

| 类型 | 已发现 | 已解释为业务含义 | 待确认 |
|---|---:|---:|---:|
| 业务对象 | | | |
| 状态 | | | |
| 业务规则 | | | |
| 配置 | | | |
| 场景 | | | |

技术元素被发现但尚未翻译成业务含义，不算“已解释”。

---

# 19. 待确认问题

输出：

`13-待确认问题.md`

如果只能确认技术行为、无法确认业务含义，必须记录：

```text
TBC-xxx
技术上观察到了什么
业务上哪里不清楚
影响哪些对象/流程
建议向谁或用什么数据确认
```

不要用技术事实填补业务空白。

# 21. 大型系统执行方式

不要一次写完整系统总结。

按业务域逐个完成：

```text
业务对象
→ 生命周期
→ 业务规则
→ 场景
→ 流程
→ 可读性检查
→ 覆盖检查
```

然后再跨域合并。

大型系统读取：
`references/大型系统分批分析指南.md`

---

# 22. 完成标准

完成不是“写了很多内容”，而是产品经理能够直接使用输出讨论改版。

必须满足：

1. 不看源码也能理解核心业务；
2. 业务对象和状态全部使用业务语言；
3. 业务流程不包含代码调用链；
4. 技术事实全部下沉到证据层；
5. 每项重要功能都解释了业务目的、条件和结果；
6. 规则、场景、异常可以直接用于后续产品抽象和TO-BE设计；
7. 无法确认的业务含义被明确标记，而不是用技术术语掩盖。

如果输出仍像“源码中文说明书”，说明逆向尚未完成。
