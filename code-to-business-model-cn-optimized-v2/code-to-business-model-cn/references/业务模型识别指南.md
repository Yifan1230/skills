# 业务模型识别指南

## 目的
帮助产品经理从大量源码线索中识别真正的业务对象，避免把数据库表、页面、接口或代码模块直接当成业务模型。

## 一、判断一个概念是不是业务对象
优先看它是否具备：
- 业务人员有明确名称；
- 有自己的身份或编号；
- 有一组业务属性；
- 会经历状态变化；
- 用户会围绕它执行创建、提交、审核、变更、关闭等操作；
- 会与其他业务对象形成稳定关系。

## 二、常见误判
- 审核记录、日志、明细通常是主对象的过程记录，不一定是一级业务对象。
- 是否允许撤回、默认配置等通常属于业务规则或配置，不一定是业务对象。
- “列表页、审核页、详情页”只是操作入口，不是业务对象。

## 三、对象分类
建议区分：
- 主对象：业务围绕其展开，如项目、学生、预警任务。
- 配置对象：定义规则，如项目种类、评审规则。
- 过程对象：记录生命周期阶段，如中期检查、专家评审任务。
- 结果对象：最终产物，如评审结果、质量报告。
- 记录：日志、历史版本、操作痕迹。

## 四、对象关系
重点识别：属于、包含、产生、依赖、关联、引用、过程归属。

最终对象模型必须能回答：系统到底在管理什么，以及这些东西之间为什么会发生关系。
