# 业务模型质量检查清单

## 1. 产品可读性

- [ ] 不看源码也能理解主要业务
- [ ] 业务正文没有字段名、表名、方法名、接口编码、状态数字
- [ ] 技术信息只存在于证据层
- [ ] 流程图使用业务动作，而不是代码调用链
- [ ] 每项重要功能都解释了业务目的、角色、对象、条件和结果
- [ ] 没有把“技术实现过程”直接当成“业务流程”

如果这一组不通过，其他内容即使技术上正确，也不能视为合格业务模型。

## 2. 业务对象

- [ ] 核心主对象已识别
- [ ] 配置对象、过程对象、结果对象、记录已区分
- [ ] 对象之间的产生、包含、归属和关联关系清楚
- [ ] 没有把页面、接口、数据表直接当成业务对象
- [ ] 对象名称是业务人员理解的名称

## 3. 生命周期

- [ ] 核心对象的主要状态都有业务含义
- [ ] 状态进入和离开条件清楚
- [ ] 驳回、撤回、停开、恢复、终止、延期等逆向路径已覆盖
- [ ] 不存在只用数字/代码表示但未翻译的状态
- [ ] 无法确认的状态已进入待确认清单

## 4. 业务规则

- [ ] 新增、修改、删除、提交、审核等关键操作都有业务前置条件
- [ ] 状态差异已覆盖
- [ ] 角色差异已覆盖
- [ ] 业务类型差异已覆盖
- [ ] 配置差异已覆盖
- [ ] 时间和数量条件已覆盖
- [ ] 规则表达是业务判断，不是字段判断的中文改写

## 5. 业务场景

- [ ] 主流程场景完整
- [ ] 重要分支场景完整
- [ ] 异常和恢复场景完整
- [ ] 角色差异场景完整
- [ ] 配置差异场景完整
- [ ] 场景能够关联到业务规则
- [ ] 没有机械穷举不存在的组合

## 6. 角色与权限

- [ ] 角色业务责任清楚
- [ ] 操作权限清楚
- [ ] 数据范围清楚
- [ ] 状态对权限的影响已说明
- [ ] 没有用权限代码替代业务权限说明

## 7. 配置

- [ ] 会改变业务流程的配置已梳理
- [ ] 配置业务含义清楚
- [ ] 配置作用范围清楚
- [ ] 不同配置产生的业务差异清楚
- [ ] 没有把参数表直接当成配置模型

## 8. 端到端流程

- [ ] 已跨页面串起完整业务过程
- [ ] 主流程与异常流程可区分
- [ ] 每个关键节点说明“谁、处理什么、什么条件、去哪”
- [ ] 流程图中没有方法名、字段名、表名和状态码

## 9. 覆盖检查

- [ ] 已发现状态无遗漏
- [ ] 已发现业务类型无遗漏
- [ ] 关键业务分支无遗漏
- [ ] 权限差异无遗漏
- [ ] 配置差异无遗漏
- [ ] 技术上发现但尚未翻译成业务含义的内容全部进入待确认

## 10. 最终判断

最终业务模型应该可以直接用于：

- 产品抽象
- TO-BE设计
- 业务评审
- 场景验收

如果下游仍然需要阅读源码才能理解，说明业务逆向没有完成。
