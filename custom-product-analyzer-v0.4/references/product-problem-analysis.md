# Product Problem Analysis

## 目的

本文件用于解决一个常见失败模式：Agent 已经识别出 Feature 和技术差异，但最终仍然只输出“配置化候选”“保留定制”等技术/分类语言，产品经理无法据此判断真正的产品问题。

最终产品分析必须回答的不是：

> 这段代码应该配置化吗？

而是：

> 哪个角色，在什么业务场景中，因为标品当前的什么限制而需要定制？多个客户是否在绕过同一个产品能力缺口？标品应该建设什么能力，才能从根本上减少这类定制？

---

## 一、六步产品翻译法

### Step 1：先说“行为变了什么”

从技术差异中提炼用户可感知行为。

技术事实：

```text
新增字段 NJ、PYCC
新增 import 校验 action
新增 errorMessage 配置
```

行为变化：

```text
导入学生名单时，会按年级、培养层次等条件判断学生是否允许导入，并针对不符合条件的学生给出提示。
```

如果无法说清行为变化，先不要进入产品判断。

### Step 2：补齐业务场景和角色

必须明确：

- 业务环节：例如学生名单导入、排课、选课、培养方案审核；
- 角色：管理员、学院秘书、教师、学生等；
- 触发时机：导入时、提交时、审核时、开放选课时等。

### Step 3：写“标品限制”而不是“代码缺口”

错误：

```text
标品没有 NJ 字段。
```

正确：

```text
标品导入校验条件固定，管理员不能按本校规则增加年级、培养层次等准入条件。
```

### Step 4：跨客户找共同根因

客户 A：按年级校验。
客户 B：按培养层次校验。
客户 C：按学籍状态校验。

不要得出三个功能：

- 增加年级校验
- 增加培养层次校验
- 增加学籍状态校验

应优先判断共同根因：

> 导入准入规则缺少可配置能力。

### Step 5：定义“优化目标”

优化目标必须从用户行为出发：

```text
管理员可以不改代码，按学校规则配置学生名单导入的准入条件、校验级别和提示信息。
```

不要只写：

```text
规则配置化。
```

### Step 6：形成产品能力方案

方案要说明“提供什么能力”，而不是“采用什么技术实现”。

例如：

```text
在学生名单导入中增加“导入校验规则配置”：
- 可选择校验字段/业务条件；
- 可配置适用范围；
- 可设置阻断或提醒；
- 可配置提示语；
- 支持多条规则组合。
```

只有在证据支持时才写具体维度，不要凭空扩展。

## 二、产品问题识别 Gate

一个差异进入“产品优化方向”前，至少满足 4 项中的 3 项：

1. 能明确用户角色；
2. 能明确业务场景；
3. 能明确用户可感知行为变化；
4. 能说明当前标品限制。

若只知道：

- 某 Java 包新增；
- 某工具库替换；
- 某类名变化；
- 某前端组件替换；
- 某依赖升级；

则默认进入 `技术差异/实现特例`，不进入产品方向。

## 三、根因抽象模式

### 1. 固定值反复被改

表面：

```text
人数 2 → 3 → 5
```

产品根因：

```text
业务参数被写死。
```

### 2. 条件维度反复增加

表面：

```text
学院 / 年级 / 培养层次 / 学位类型
```

产品根因：

```text
规则条件不可配置或配置维度不足。
```

### 3. 流程节点反复增删/换序

产品根因：

```text
流程与固定阶段强绑定，缺少流程编排能力。
```

### 4. 页面字段反复增删

产品根因可能是：

```text
表单字段扩展能力不足。
```

但先判断是否只是客户个性展示需求。

### 5. 权限范围反复调整

产品根因可能是：

```text
权限粒度或授权对象模型不足。
```

### 6. 不同学校反复改校验

产品根因通常不是“缺某条校验”，而是：

```text
校验规则不可组合、不可配置，或缺少规则生效范围。
```

### 7. 不同客户反复复制整应用

不能直接得出“应用要重做”。需继续判断复制的共同变化集中在哪：

- 流程？
- 规则？
- 数据字段？
- 页面布局？
- 权限？

只有共同变化点才是产品问题。

## 四、用户可见语言规范

### 禁止作为产品问题标题

- configuration_candidate
- keep_custom
- observe
- 版本漂移项
- Java 类名
- jar/工具库名
- EDM/EPM/EDA/EPG
- SQL/表名/字段名
- 某某 service/controller

### 推荐标题结构

```text
<业务对象/环节> + <当前限制>
```

示例：

- 学生名单导入校验规则固定，无法适配不同学校准入要求
- 选课限制条件写死，新增控制维度需要重复定制
- 排课约束分散在多个页面和规则中，缺少统一配置入口
- 审核流程节点固定，学校差异只能通过改代码处理

---

## 五、优化方案语言规范

方案必须回答：

1. 产品增加什么入口/能力；
2. 谁可以配置/使用；
3. 配什么；
4. 作用于什么范围；
5. 达到什么业务效果。

例如：

```text
建议在“学生名单导入”中增加校验规则配置能力，由管理员按业务场景配置准入条件、阻断/提醒级别、适用范围和提示语，使不同学校的导入规则可以通过配置适配，而不再为每一条规则修改代码。
```

## 六、技术特例的处理

以下内容默认不进入产品方向：

- hutool 等工具库嵌入；
- XHCOM 等仅能识别为技术模块名、无法还原业务行为的内容；
- 依赖升级；
- 框架兼容；
- 性能实现差异；
- 打包方式；
- 非用户可感知的重构。

它们应进入报告后部：

```text
技术差异 / 实现特例
```

如果后续发现这些技术变化实际上支撑了新的业务行为，再重新提升为 Change Unit / Feature。

## 七、输出示例

### 不合格

| Feature | 建议 | 置信度 |
|---|---|---|
| 学生名单导入验证规则 | configuration_candidate | high |
| 排课教室/前端/日期控制等版本漂移项 | observe | medium |
| NJU hutool 嵌入、XHCOM 等定制模块 | keep_custom | high |

### 合格

| 产品问题 | 客户定制共性 | 根因判断 | 优化方向 | 建议类型 | 置信度 |
|---|---|---|---|---|---|
| 学生名单导入校验规则固定，无法适配不同学校的名单准入要求 | 多个客户分别增加学籍状态、年级、培养层次等导入校验 | 校验条件和生效范围被写死 | 增加“导入校验规则配置”，允许管理员配置条件、阻断/提醒、提示语和适用范围 | 建议做成可配置能力 | 高 |
| 排课中的教室、开放端、日期等控制项在不同客户反复变化 | 多客户调整不同排课约束，但目前证据尚不足以确认是否属于同一业务规则体系 | 可能缺少统一的排课约束配置，但现有差异可能混有版本升级 | 继续收集同版本客户证据，先归并为“排课约束规则”候选，不立即进入开发 | 证据不足，继续观察 | 中 |

`hutool`、`XHCOM` 等纯技术项不进入此表。
