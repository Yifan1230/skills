# Product Problem Synthesis — 强制产品经理抽象层

## 目的

技术分析只能回答“哪里变了”，不能直接回答“产品哪里有问题”。

从 V0.3 起，禁止直接把 Feature / Change Unit / 技术差异写进产品经理主报告。
必须先生成独立的 `Product Problem Card`，再由这些卡片生成主报告。

分析链必须是：

```text
技术证据
→ 用户可感知行为
→ 业务角色与场景
→ 当前标品表现
→ 客户为什么要改
→ 多客户共同变化
→ 产品根因
→ 优化目标
→ 产品能力方案
→ 产品经理可判断结论
```

---

# 一、产品问题不是 Feature 的改名

以下转换无效：

```text
Feature：学生名单导入验证规则
↓
产品问题：学生名单导入验证规则需要配置化
```

这只是改了标题。

真正的产品问题必须包含：

> 谁，在什么业务场景中，因为标品当前的什么限制，导致什么业务结果/管理成本/实施定制。

例如（仅为表达形式示例，不代表代码事实）：

```text
某管理角色在导入学生名单时，不同学校需要执行不同的名单准入判断，
但标品校验口径固定，新增或调整规则需要修改代码。
```

只有证据能支持“角色、场景、限制”时，才可以形成正式产品问题。

---

# 二、先恢复业务语义，再谈产品方向

对每个高频 Feature Cluster，必须先收集 `Business Evidence Pack`：

1. 页面标题、菜单名称；
2. 按钮文字；
3. 字段中文名称；
4. 提示语、错误信息；
5. 字典名称和值；
6. permission/menu 文本；
7. JS/JSP/EPG 中用户可见中文；
8. Action 名称及上下文；
9. 表/字段注释；
10. version/change_reference 说明；
11. 多客户之间具体行为差异。

如果只知道：

```text
v_by_jxrw → c_pygl_rwgl_rwx
```

但无法确认两个视图在业务上分别代表什么，则不能直接写：

> “标品名单准入规则固定”。

正确处理是：

```text
状态：needs_business_confirmation

已确认：
多个客户在名单导入相关数据选择/校验逻辑上存在差异。

尚未确认：
这些差异分别对应哪一种业务准入规则、由哪个角色配置、何时触发。

下一步：
继续追踪页面文案、错误提示、数据模型字段中文名或由产品经理补充业务含义。
```

产品语言不能以“听起来合理”为标准，必须以证据为标准。

---

# 三、Product Problem Gate（硬门槛）

进入“产品优化建议主表”必须同时满足：

1. `business_scenario` 非空；
2. `actor` 非空，或明确写“角色待确认”且不进入正式候选；
3. `current_standard_limitation` 非空；
4. `customer_variation_summary` 至少包含 2 个独立客户，或存在明确业务文档；
5. `root_product_gap` 能用非技术语言表达；
6. `proposed_product_capability` 能描述产品提供什么能力；
7. 不依赖 Java/XML/表名/工具库才能解释问题。

若不满足：

- `needs_business_confirmation`：业务语义不足；
- `technical_only`：纯技术实现；
- `version_noise`：版本差异/共识基线噪声。

这些不得进入正式产品化候选主表。

---

# 四、根因抽象必须比“配置化”更具体

不合格：

```text
根因：缺少配置能力
方案：做成配置化
```

合格：

```text
根因：
名单准入判断的条件、作用范围和处理结果被固定在程序逻辑中，
管理员无法根据本校管理规则组合或调整。

优化目标：
管理员能够不改代码维护名单准入规则。

产品能力：
在名单导入功能中提供规则维护入口，
支持配置适用范围、判断条件、处理方式（阻断/提醒）和提示语。
```

“配置化”只是实现方向，不是产品问题本身。

---

# 五、主报告只回答产品经理真正要判断的 5 件事

每个正式候选必须让产品经理一眼看到：

### 1. 到底哪里不好用？
产品问题。

### 2. 哪些客户为什么都改过？
共性证据。

### 3. 根因是什么？
是参数写死、规则维度不足、流程强绑定、表单扩展不足、权限粒度不足，还是其他。

### 4. 标品应该变成什么样？
用户未来如何使用。

### 5. 是否值得做？
证据强度、客户覆盖、风险、待确认项。

# 六、产品问题标题规则

推荐：

```text
<业务环节> + <标品限制/业务后果>
```

例如：

- 名单导入规则固定，不同学校的准入要求需要重复定制
- 选课限制条件缺少组合能力，新增控制维度必须改代码
- 排课约束缺少统一维护入口，规则散落导致学校差异难以配置
- 审核节点与固定阶段强绑定，流程调整必须定制

禁止：

- 学生名单导入验证规则
- F-001
- CU-008
- 排课教室/前端/日期控制版本漂移项
- hutool 嵌入
- XHCOM 模块
- SkjcPo.epm
- jxrwjccx.eda

# 七、技术项分流

以下默认进入技术附录：

- 工具库嵌入；
- Java 包变化；
- 依赖版本；
- Hash 分发簇；
- 类文件修改；
- 定时器实现类；
- 技术模块名；
- 框架兼容；
- 性能优化；
- 无业务行为证据的新增模块。

只有追踪到明确用户行为后，才能升级为产品问题。

---

# 八、推荐输出结构

正式主表只保留：

| 产品问题 | 业务影响 | 多客户共性 | 产品根因 | 建议产品能力 | 建议动作 | 证据强度 |
|---|---|---|---|---|---|---|

不要出现：

- Feature 列；
- 内部英文推荐枚举；
- 类名/文件名；
- 版本 Hash；
- 技术模块名。

详细技术证据全部放后文“证据附录”。
