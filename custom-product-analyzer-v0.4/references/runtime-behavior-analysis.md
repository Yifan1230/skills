# Runtime Behavior Analysis — 产品分析的核心对象

## 核心原则

产品经理不关心“代码改了什么”，首先关心：

> 标品运行时怎么表现？客户版本运行时怎么表现？用户实际感知到的差异是什么？

因此 V0.4 中，技术 Diff 只能作为证据来源，不能直接生成 Feature 或产品结论。

强制链路改为：

```text
Technical Diff
→ Runtime Behavior Evidence
→ Behavior Delta
→ Business Capability / Feature
→ Product Problem
→ Product Optimization
```

---

# 一、Behavior Delta 是什么

Behavior Delta = 同一业务场景下，标品与客户版本在运行时行为上的差异。

必须用业务动作描述，而不是文件动作描述。

## 不合格

```text
修改 XsmdImportValidate.java
替换查询视图
新增一个 EDA action
增加一个 NJ 字段
修改前端 JS
```

## 合格

```text
标品：
导入学生名单时，只允许从 A 范围选择学生。

客户版本：
导入名单时，允许从 B 范围选择学生，并增加某类学生过滤条件。

用户感知：
管理员可导入的学生范围发生变化。
```

或者：

```text
标品：
排课时只能按固定日期范围安排。

客户版本：
允许按学院/教学任务设置不同日期范围。

用户感知：
排课管理员可控制的排课时间范围由“全局固定”变为“按业务对象分别控制”。
```

# 二、每个差异必须回答 7 个运行时问题

对每一个候选差异，必须尽量回答：

1. **角色（Actor）**
   谁在使用：管理员、教师、学生、专家等。

2. **触发场景（Trigger）**
   在什么操作下发生：导入、提交、审核、选课、排课、查询、导出等。

3. **输入/前置条件（Input / Preconditions）**
   用户输入什么、选择什么、当前对象是什么状态。

4. **标品行为（Standard Behavior）**
   标品运行时如何判断、展示、限制或处理。

5. **客户行为（Variant Behavior）**
   客户版本运行时如何判断、展示、限制或处理。

6. **用户可感知差异（User-visible Difference）**
   用户最终看到、能做、不能做、得到的结果有什么不同。

7. **业务结果差异（Business Outcome）**
   这个差异改变了什么管理口径、业务范围、流程结果或操作成本。

至少第 4、5、6 项明确，才能生成正式 Behavior Delta。

---

# 三、优先恢复“行为”，不要优先恢复“代码结构”

Agent 读取技术差异后，应主动寻找能证明运行行为的证据：

## 高价值证据

- 页面标题
- 按钮名称
- 表单字段中文名
- 是否显示/隐藏
- 是否可编辑
- 默认值
- 下拉选项
- 查询条件
- 校验提示
- 错误提示
- 成功提示
- 状态值
- 权限控制
- 流程节点
- SQL where 条件
- if/else 判断
- 返回值
- 导入/导出字段
- 页面跳转
- Action 入参/出参
- 数据范围变化

## 低价值证据

- 类名变化
- 方法重命名
- 包移动
- 工具库替换
- 依赖升级
- Hash 不一致
- XML 文件数量变化

低价值证据只能作为补充，不可单独形成产品结论。

# 四、行为差异分类

Behavior Delta 至少归入以下一种：

### 1. 可见内容变化
用户看到的字段、选项、提示、列表列发生变化。

### 2. 可操作范围变化
用户能操作哪些对象/学生/课程/任务发生变化。

### 3. 判断规则变化
同样输入下，允许/禁止/提醒结果发生变化。

### 4. 流程变化
步骤、审核节点、顺序、跳转条件发生变化。

### 5. 数据范围变化
查询、统计、导入、导出的数据范围发生变化。

### 6. 权限变化
不同角色可见、可操作的内容发生变化。

### 7. 默认行为变化
默认值、默认筛选、默认状态、默认处理方式变化。

### 8. 计算口径变化
统计、排序、汇总、评分、计算方式变化。

### 9. 时序变化
何时可操作、截止时间、时间窗口、定时处理发生变化。

### 10. 外部交互变化
第三方系统、接口、通知、同步行为变化。

# 五、从代码到行为的转换规则

## 条件变化

代码：

```text
where 条件新增 PYCC / NJ
```

不能直接写：

> 新增培养层次、年级字段。

应进一步判断：

```text
查询/选择范围是否因此缩小或扩大？
用户是否可以按培养层次/年级筛选？
这些条件是固定判断还是可配置条件？
```

输出：

```text
行为差异：
可参与选课/可被选入名单的对象范围增加了培养层次、年级限制。
```

---

## View / SQL 替换

代码：

```text
v_by_jxrw → c_pygl_rwgl_rwx
```

不能写：

> 客户替换了视图。

必须回答：

```text
两个数据源返回的业务对象范围有什么区别？
多了哪些学生/课程/任务？
少了哪些？
用户最终可看到/可操作的对象有什么不同？
```

如果无法确认：

```text
behavior_status = unknown
```

不进入产品建议。

---

## 前端控制变化

代码：

```text
if (...) hide button
```

输出：

```text
标品：
角色 A 在状态 X 下可以看到并点击“提交”。

客户版本：
状态 X 下按钮隐藏，只有状态 Y 才能提交。

用户可感知差异：
提交动作的开放条件发生变化。
```

---

## 字段变化

代码：

```text
新增 NJ 字段
```

不能写：

> 增加年级字段。

要确认它用于：

- 展示？
- 筛选？
- 校验？
- 分组？
- 权限？
- 计算？
- 流程判断？

只有确认用途后才能输出产品行为。

---

# 六、Behavior Delta Gate

进入 Feature/Product Problem 分析前，必须满足：

```text
standard_behavior
variant_behavior
user_visible_difference
```

至少三个字段都有内容。

否则：

```text
behavior_status = insufficient_evidence
```

并进入“行为语义待确认”。

---

# 七、产品问题必须建立在行为差异上

正确：

```text
多个客户都改变了“名单中哪些学生可被导入”的判断口径
↓
不同学校需要不同名单准入规则
↓
标品当前把准入规则固定在实现中
↓
产品问题：名单准入规则缺少可维护能力
```

错误：

```text
21 个客户都改了 XsmdImportValidate.java
↓
名单校验应该配置化
```

客户数量只能证明“技术改动重复”，不能自动证明“业务问题相同”。

---

# 八、最终报告的核心表达

主报告里每个候选首先展示：

### 标品怎么运行
自然语言说明。

### 客户版本怎么运行
说明行为差异，不写代码。

### 用户感知到什么不同
能做/不能做/看到什么/结果是什么。

### 多客户共同变化
比较不同客户 Behavior Delta，而不是比较文件。

### 产品根因
为什么标品会导致这些重复变化。

### 优化后的理想行为
未来标品运行时应该如何表现。

---

# 九、产品经理主表推荐格式

| 业务场景 | 标品当前行为 | 客户版本行为 | 用户感知差异 | 共性问题 | 建议优化后的行为 | 证据客户 |
|---|---|---|---|---|---|---|

注意：

这一张表比“Feature → 产品化建议”优先级更高。
