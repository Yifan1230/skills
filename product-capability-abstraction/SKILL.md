# Product Capability Abstraction

## 1. 目标

回答：

> **新产品应该沉淀哪些业务能力，这些能力应该固定、配置、组合、扩展、定制还是废弃？**

本 Skill 不重新读源码，不直接画页面。

---

# 2. 输入契约

优先消费以下“业务语义层”输入：

- AS-IS业务对象模型；
- 生命周期；
- 业务规则；
- 业务场景；
- 配置模型；
- 定制差异；
- 已确认问题。

如果输入大量出现：

```text
字段名 / 表名 / 方法名 / 状态码 / 接口编码
```

不要直接据此抽象产品能力。

应先要求上游业务逆向 Agent 完成业务翻译。

技术证据只用于核验某个业务结论，不作为产品能力命名依据。

---

# 3. 产品可读性要求

产品能力名称必须是业务人员能理解的概念，例如：

```text
专家评审
评审规则
专家分配
结果确认
整体调课
合班排课
教学任务停开
```

禁止把以下内容当成产品能力：

```text
validateCanEdit
copyForHbpk
T_XXX
SFXS
状态99
```

如果只能用技术名才能描述某项能力，说明业务含义还没有抽象完成。

---

# 4. 六类产品化结果

每项现有业务能力或差异，尽量归入：

```text
标准能力
配置能力
组合能力
扩展能力
定制能力
废弃能力
待验证
```

## 标准能力
业务含义稳定、目标客户普遍需要，应由产品直接提供。

## 配置能力
业务目的相同，但参数、规则、流程、表单或权限存在稳定差异。

## 组合能力
多个稳定能力可以组合成不同业务场景。

## 扩展能力
低频但有复用价值，适合通过扩展点接入。

## 定制能力
强客户特例，难以合理抽象，不应污染核心产品。

## 废弃能力
历史包袱、重复能力或与目标产品方向冲突。

---

# 5. 分析顺序

```text
业务能力盘点
→ 差异归因
→ 共性判断
→ 能力拆分/合并
→ 产品化分类
→ 配置层级
→ 默认策略
→ 复杂度检查
→ 产品边界
```

不要从“某客户改了某个字段”直接跳到“做一个配置项”。

先翻译成：

> 这个客户在业务规则上到底有什么不同？

---

# 6. 差异分类

优先按业务含义分类：

| 差异类型 | 例子 |
|---|---|
| 参数差异 | 专家数量不同 |
| 规则差异 | 是否允许撤回 |
| 流程差异 | 两级审核/三级审核 |
| 表单差异 | 需要提交的材料不同 |
| 权限差异 | 学院是否能修改结果 |
| 数据范围差异 | 本学院/全校/指定对象 |
| 展示差异 | 列表字段和排序不同 |
| 集成差异 | 是否接外部平台 |

技术实现差异不等于产品差异。

例如两个客户用了不同字段，但业务规则完全相同，则不要创造两个产品能力。

---

# 7. 配置化判断

每提出一个配置项，至少问：

1. 是否在多个客户重复出现？
2. 是否是业务人员能够理解和维护的差异？
3. 是否有合理默认值？
4. 配错会造成什么业务后果？
5. 是否可以通过更好的标准模型消除差异？
6. 是否会和其他配置形成组合爆炸？
7. 谁维护？多久调整一次？

不要把“技术上能做成参数”当成“产品上应该配置”。

---

# 8. 配置层级

常见层级：

```text
系统全局
→ 业务类型/种类
→ 业务批次
→ 组织/院系
→ 具体业务对象
→ 用户个人
```

规则应放在：

> 最稳定、最符合业务归属、又能覆盖真实差异的层级。

正文只使用业务层级名称，不使用配置表或字段名称。

---

# 9. 能力拆分原则

不要按旧页面、旧接口或代码模块拆能力。

优先依据：

```text
业务对象
+
核心业务动作
+
稳定业务规则
```

例如一个旧“评审设置”功能，可能应拆成：

```text
评审规则
专家分配
评分标准
评审执行
结果确认
```

是否拆分取决于业务责任、变化频率和配置层级，而不是代码目录。

---

# 10. 产品能力地图

输出应类似：

```text
专家评审
├─ 评审规则【标准框架+配置】
├─ 专家分配【标准能力】
├─ 盲审【配置能力】
├─ 评分标准【配置能力】
├─ 结果确认【标准能力】
└─ 外部送审【扩展能力】
```

不要输出：

```text
ReviewService
ReviewMapper
T_REVIEW_CFG
```

---

# 11. 核心输出矩阵

| 业务能力/差异 | 业务差异类型 | 共性程度 | 产品策略 | 配置层级 | 默认策略 | 业务证据 | 风险 |
|---|---|---|---|---|---|---|---|

“业务证据”优先引用上游业务规则/场景编号。

如果需要下钻技术来源，只引用证据编号，不在主矩阵展开代码细节。

---

# 12. 配置复杂度检查

当配置增多时，检查：

- 是否互相依赖；
- 是否存在非法组合；
- 是否需要模板；
- 是否需要推荐默认方案；
- 是否需要高级配置分层；
- 是否需要影响预览和冲突校验。

目标：

> **标准场景开箱即用，复杂差异按需展开。**

---

# 13. 与TO-BE的边界

本 Skill 可以决定：

- 能力怎么分类；
- 哪些对象可能需要拆分/合并；
- 配置归属层级；
- 哪些旧能力不应进入标品。

但不负责：

- 全量TO-BE状态机；
- 完整新流程；
- 页面交互。

---

# 14. 产品可读性 Gate

提交前检查：

- 能力名称是否都是业务概念？
- 是否存在字段名/表名/方法名直接充当能力名？
- 差异是否解释了业务含义，而不是技术改动？
- 配置是否说明“业务上控制什么”？
- 产品经理不看源码能否讨论这份能力地图？

任一不满足，退回重写。

---

# 16. 完成标准

完成后应能直接回答：

1. 哪些是标准能力？
2. 哪些差异值得配置？
3. 配置应放在哪一层？
4. 哪些能力适合组合？
5. 哪些应通过扩展点解决？
6. 哪些客户特例不进入标品？
7. 哪些历史能力应废弃？
8. 默认方案是什么？

如果答案仍依赖理解字段、表或方法，说明产品抽象尚未完成。
