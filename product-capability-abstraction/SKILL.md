# Product Capability Abstraction

## 1. 目标

把“旧系统有什么”和“客户改了什么”，转换成：

> **新产品应该沉淀什么能力，以及这些能力应该固定、配置、组合、扩展还是放弃。**

本 Skill 不负责重新梳理源码，也不负责直接画页面。

输入应优先来自：

- AS-IS业务对象模型
- 生命周期和业务规则
- 业务场景库
- 定制差异分析
- 已确认的现状问题

---

## 2. 核心输出

最终至少形成：

1. 产品能力地图
2. 差异模式分类
3. 能力产品化策略矩阵
4. 配置边界与配置层级
5. 标准/配置/组合/扩展/定制/废弃清单
6. 高争议能力决策建议
7. 仍待验证的产品假设

---

# 3. 六类产品化结果

每项现有能力或差异，尽量归入以下之一。

## 3.1 标准能力

定义：大多数目标客户都需要，业务含义稳定，不应让客户重复配置其核心逻辑。

例如：

- 项目申请必须归属于某个批次；
- 审核结果必须可追溯；
- 课程必须有课程基本信息。

判断重点：

> 如果把它做成可配置，会不会只是把产品应承担的共性责任转嫁给实施？

---

## 3.2 配置能力

定义：业务目的相同，但不同客户在参数、规则、流程或展示上存在稳定差异。

典型：

- 是否需要专家评审；
- 每项目专家数量；
- 审核层级；
- 是否允许撤回；
- 表单字段要求。

配置必须说明作用层级和默认值。

---

## 3.3 组合能力

定义：由多个稳定业务能力组合形成不同业务场景。

例如：

```text
报名 + 材料审核 + 专家评审 + 结果确认
```

可组合形成某类招生/项目申报场景。

组合不是“任意拼装”，必须有明确业务约束。

---

## 3.4 扩展能力

定义：不是主流共性，但具有复用价值，适合通过扩展点接入而不是污染主模型。

例如：

- 第三方送审平台；
- 特殊签章；
- 外部科研数据匹配。

---

## 3.5 定制能力

定义：低频、强客户特有、难以抽象且进入标品会显著增加整体复杂度。

不要因为已经开发过，就默认应该产品化。

---

## 3.6 废弃能力

定义：历史包袱、低价值重复能力、已有更合理替代方案，或与目标产品方向冲突。

废弃必须记录：

- 为什么废弃；
- 哪些客户仍在使用；
- 是否需要迁移/兼容。

---

# 4. 分析顺序

严格按照：

```text
现有能力盘点
→ 差异归因
→ 共性判断
→ 能力拆分
→ 产品化分类
→ 配置层级
→ 默认策略
→ 复杂度检查
→ 输出边界
```

不要直接从“客户A要什么”跳到“做一个配置项”。

---

# 5. 先判断差异是什么

同一个“客户不同”可能属于完全不同的问题。

优先分类：

| 差异类型 | 典型问题 |
|---|---|
| 参数差异 | 专家数2/3/5人 |
| 规则差异 | 是否允许撤回 |
| 流程差异 | 两级审核/三级审核 |
| 表单差异 | 不同学校要求不同材料 |
| 权限差异 | 学院是否能修改结果 |
| 数据差异 | 对象范围、数据来源不同 |
| 展示差异 | 列表字段、排序不同 |
| 集成差异 | 是否接外部平台 |

分类方法参考：

`references/difference-patterns.md`

---

# 6. 不要把所有差异都做成配置

每提出一个配置项，至少问：

1. 这个差异是否在多个客户重复出现？
2. 用户能否理解配置含义？
3. 配置错误的后果有多严重？
4. 是否有合理默认值？
5. 是否可以通过更好的标准模型消除差异？
6. 配置会不会与其他配置形成难以控制的组合爆炸？
7. 这个配置由谁维护？
8. 多久会调整一次？

如果只是为了“什么都支持”，不要直接配置化。

---

# 7. 配置层级

每个配置必须明确归属层级。

常见层级：

```text
系统全局
→ 业务类型/种类
→ 业务批次
→ 组织/院系
→ 具体对象
→ 用户个人
```

判断原则：

> 把规则放在“最稳定、最符合业务归属、又能覆盖差异”的层级。

例如：

- “是否需要专家评审”如果对某类项目长期稳定，优先归项目种类；
- “本批次评审时间”显然归项目批次；
- “专家本人的最大评审量”可能归评审执行规则。

详细参考：

`references/config-boundaries.md`

---

# 8. 能力拆分原则

不要按旧页面拆能力。

优先按：

```text
业务对象
+ 核心动作
+ 稳定业务规则
```

例如旧系统一个“评审设置页面”可能需要拆成：

```text
评审规则
专家分配
评审执行
评分标准
结果确认
```

如果这些部分变化频率和归属层级不同，就不应被一个“大配置页”绑死。

---

# 9. 判断共性的证据

共性不能只靠“感觉多数学校应该这样”。

可以使用：

- 多客户定制重复率；
- 业务流程一致性；
- 政策/行业约束；
- 核心业务对象关系；
- 用户角色职责；
- 长期版本演进；
- 实施反馈；
- 高频售前需求。

标记：

```text
高置信共性
中置信共性
待验证假设
```

---

# 10. 产品能力地图

建议输出：

```text
业务域
├─ 核心对象
│  ├─ 标准能力
│  ├─ 配置能力
│  └─ 扩展能力
└─ 跨域能力
```

例如：

```text
专家评审
├─ 评审规则【标准框架+配置】
├─ 专家分配【标准能力】
├─ 盲审【可配置】
├─ 评分指标【可配置】
├─ 结果确认【标准能力】
└─ 外部送审【扩展能力】
```

---

# 11. 核心输出矩阵

使用：

| 现有能力/差异 | 差异类型 | 共性程度 | 产品策略 | 配置层级 | 默认策略 | 证据 | 风险 |
|---|---|---|---|---|---|---|---|

产品策略只能从以下集合中优先选择：

```text
标准
配置
组合
扩展
定制
废弃
待验证
```

---

# 12. 配置复杂度检查

当配置越来越多时，必须检查：

- 配置是否互相依赖；
- 是否存在冲突组合；
- 是否需要条件显示；
- 是否需要模板/预设；
- 是否需要按学校类型提供默认方案；
- 是否需要限制高级配置只对特定管理员开放。

目标不是“配置项数量最大”，而是：

> 默认开箱即用，复杂场景才逐步展开。

---

# 13. 与TO-BE设计的边界

本 Skill 可以输出：

- 能力应该怎么分类；
- 配置应归哪个层级；
- 哪些旧对象需要拆分/合并的建议；
- 需要TO-BE重点解决的问题。

但不要直接完成：

- 全量TO-BE状态机；
- 完整新流程；
- 页面和交互设计。

这些交给下游 TO-BE 和 UX Agent。

---

# 14. 待验证假设

以下情况不要强行定型：

- 只有一个客户案例；
- 业务数据量不足；
- 多客户做法互相矛盾；
- 政策/业务口径尚未确认；
- 差异可能只是旧产品限制导致。

统一输出：

```text
HYP-001
假设
证据
反证
需要验证什么
验证方式
```

# 16. 完成标准

完成后应能明确回答：

1. 哪些是必须沉淀的标准能力？
2. 哪些差异值得配置？
3. 每个配置应该放在哪一层？
4. 哪些能力应该组合而不是复制开发？
5. 哪些需求应该通过扩展点解决？
6. 哪些客户特例不应该进入标品？
7. 哪些历史能力应该废弃？
8. 默认方案是什么？
9. 哪些判断仍只是产品假设？

如果最后答案只是“做成更灵活的配置”，说明抽象仍然不够。
