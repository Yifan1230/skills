# Product UX Architecture

## 1. 目标

把稳定的 TO-BE 业务模型转化成用户能够高效理解和完成业务的产品结构。

本 Skill 回答：

- 用户从哪里进入业务场景？
- 工作台应该优先展示什么？
- 信息架构如何组织？
- 完成一件事需要经过哪些页面？
- 高频任务如何缩短路径？
- 多角色、多身份如何组织而不混乱？
- 数据如何继续驱动行动？
- AI如何嵌入具体业务节点？

本 Skill 不重新定义核心业务对象、生命周期和业务规则。

---

# 2. 输入契约

优先使用：

- TO-BE业务对象；
- 生命周期；
- 角色职责；
- 业务规则；
- 场景库；
- 端到端流程；
- 配置边界；
- 现状体验问题。

如果输入仍然以字段名、接口名、方法名、状态码为主，先退回TO-BE/业务逆向阶段完成业务语义翻译。

UX不负责替技术命名“美化中文”，而是基于业务概念重新组织用户体验。

---

# 3. 产品可读性规则

页面、菜单、按钮、状态、提示语必须优先使用用户和业务人员理解的词。

推荐：

```text
停开教学任务
恢复开课
整体调课
合班排课
待学院审核
```

不要直接沿用：

```text
SFXS
ZT
copyForHbpk
validateCanEdit
状态99
```

技术限制如果必须影响体验，应翻译成用户能理解的原因。

例如：

错误：
> validateCanEdit失败。

正确：
> 当前教学任务已锁定，暂不能修改排课安排。

---

# 4. 六条核心设计原则

## 4.1 场景驱动

优先围绕：

> 用户现在要完成什么事情？

而不是复制旧菜单。

## 4.2 角色驱动

不同角色的工作台、任务优先级、数据范围和操作入口应不同。

## 4.3 任务驱动

形成：

```text
业务事件
→ 产生任务
→ 用户直接办理
→ 状态变化
→ 下一任务
```

## 4.4 默认简单，复杂按需展开

标准路径应简单；高级配置和低频操作按需展开。

## 4.5 数据到行动

不要只展示数字，要支持：

```text
发现
→ 定位
→ 判断
→ 行动
→ 反馈
```

## 4.6 AI嵌入业务节点

AI优先减少寻找、录入、校验、整理和判断成本。

高责任动作应采用：

```text
AI建议
+ 原因
+ 影响范围
+ 人工确认
```

---

# 5. 先做角色任务地图

| 角色 | 高频任务 | 周期任务 | 异常任务 | 关注数据 | 协作对象 |
|---|---|---|---|---|---|

工作台不是功能收藏夹，而是角色当前工作的组织方式。

---

# 6. 工作台设计

优先考虑：

```text
当前最重要任务
即将截止事项
异常/风险
业务进度
常用入口
关键数据
```

不要把所有模块做成同权重宫格。

---

# 7. 多身份设计

目标：减少频繁切换，但保留责任边界。

推荐：

```text
账号统一
任务整合
场景分组
责任身份可感知
数据权限仍隔离
```

高责任操作时，应让用户知道自己当前以什么业务身份处理。

---

# 8. 信息架构

IA应从以下内容推导：

```text
角色任务
+ 业务对象
+ 生命周期
+ 使用频率
```

建议区分：

### 工作入口
待办、任务、常用场景。

### 业务管理
围绕核心业务对象和流程。

### 数据与分析
监控、异常、画像、报告。

### 规则与配置
低频管理操作，与日常业务分离。

不要使用代码模块、数据库模块或接口分组作为导航依据。

---

# 9. 页面结构

每个页面先定义：

```text
页面目的
主要角色
主要业务对象
流程阶段
主任务
次任务
关键业务状态
```

再设计：

- 信息区域；
- 主操作；
- 次操作；
- 批量操作；
- 筛选条件；
- 状态反馈；
- 异常提示。

不要先确定UI布局，再找业务填进去。

---

# 10. 业务限制必须翻译成用户原因

如果某操作被禁止，提示应回答：

```text
为什么不能做
当前卡在哪
需要什么条件
下一步怎么办
```

例如：

> 当前不在学生名单维护期，暂不能增删学生。名单开放后可继续维护。

不要展示内部校验函数、代码值或系统参数名称。

---

# 11. 主操作和批量操作

区分：

- 主操作；
- 次操作；
- 危险操作；
- 高级操作。

管理端重点检查：

- 批量选择；
- 批量审核；
- 批量提醒；
- 批量导入/导出；
- 批量调整；
- 批量异常处理。

批量动作必须说明：

- 作用范围；
- 不满足条件的对象怎么办；
- 部分成功怎么办；
- 是否可撤销；
- 是否需要结果报告。

---

# 12. 流程可视化

长流程优先展示：

- 当前阶段；
- 已完成阶段；
- 下一阶段；
- 当前责任人/角色；
- 截止时间；
- 阻塞原因。

用户关心的是：

> 现在到哪、为什么卡住、谁处理、下一步是什么。

不是“状态字段是什么值”。

---

# 13. 配置端体验

推荐：

```text
推荐模板
→ 核心配置
→ 高级配置
→ 影响预览
→ 冲突校验
→ 发布/生效
```

配置名称必须说明业务含义和影响范围。

不要直接把底层参数表做成配置页面。

---

# 14. 数据与AI

## 数据

指标应尽量支持：

```text
数字
→ 对象明细
→ 责任人
→ 处理动作
→ 结果跟踪
```

## AI

适合：

- 找服务；
- 业务咨询；
- 查询分析；
- 预填；
- 校验；
- 辅助办理；
- 推荐方案。

复杂正式业务仍应进入结构化确认流程。

---

# 15. 体验评审维度

| 维度 | 核心问题 |
|---|---|
| 找到 | 用户能快速找到入口吗？ |
| 理解 | 看得懂当前发生什么吗？ |
| 判断 | 规则和原因清楚吗？ |
| 操作 | 高频路径够短吗？ |
| 批量 | 管理端能高效处理吗？ |
| 异常 | 失败后知道怎么办吗？ |
| 反馈 | 结果和下一步清楚吗？ |
| 数据 | 能从数据继续行动吗？ |
| AI | 是否减少真实工作量？ |

---

# 16. Product Readability Gate

提交前检查：

- 页面/按钮/状态名称是否来自业务语言？
- 是否出现内部字段、方法、接口、状态码？
- 错误提示是否说明业务原因而非技术错误？
- 流程图是否全部使用业务动作？
- 用户不懂代码是否仍能完整理解？

如果不能，通过修改文案无法解决时，应退回TO-BE/业务模型阶段，而不是在UX层硬解释。

# 18. 不做什么

本 Skill 不应：

- 静默改变TO-BE业务规则；
- 为了页面简单删除真实业务场景；
- 把所有能力塞进首页；
- 把技术命名直接暴露给用户；
- 把AI当所有交互的替代；
- 只做视觉风格升级。

---

# 19. 完成标准

完成后应能回答：

1. 每类角色首先看到什么？
2. 高频任务是否快速？
3. 长流程是否看得懂当前位置和下一步？
4. 多身份是否减少切换但责任仍清晰？
5. 管理端批量处理是否高效？
6. 数据是否能驱动行动？
7. 配置复杂度是否收敛？
8. 页面和提示是否完全使用业务语言？
9. AI是否减少真实工作量？

如果产品经理或用户仍需要理解字段、状态码或方法名才能使用设计，UX不合格。
