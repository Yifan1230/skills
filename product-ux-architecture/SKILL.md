# Product UX Architecture

## 1. 目标

把已确认的 TO-BE 业务模型转化成用户能够高效理解和办理业务的产品结构。

本 Skill 重点回答：

- 用户从哪里进入一个业务场景？
- 首页/工作台应该展示什么？
- 菜单和信息架构如何组织？
- 用户完成一件事需要经过哪些页面？
- 高频操作如何缩短路径？
- 多角色、多身份如何组织而不混乱？
- 数据展示如何继续产生行动？
- AI如何嵌入具体业务节点？

本 Skill 不重新定义核心业务对象和生命周期。

---

## 2. 输入前提

优先输入：

- TO-BE业务对象
- 生命周期
- 角色职责
- 业务规则
- 场景库
- 端到端流程
- 配置边界
- 现状体验问题

如果核心对象和流程仍频繁变化，应先返回 TO-BE 业务设计，不要用页面方案掩盖业务不稳定。

---

# 3. 六条核心设计原则

## 3.1 场景驱动，而不是功能堆砌

不要只按后台功能模块组织产品。

优先回答：

> 用户现在想完成什么事情？

例如：

```text
我要完成毕业审核
```

比：

```text
成绩管理
学分管理
论文管理
毕业管理
```

更接近用户任务。

---

## 3.2 角色驱动，而不是所有人一套界面

不同角色重点不同：

- 学生关注自己的任务和进度；
- 教师关注教学任务和待处理事项；
- 导师关注学生、指导任务和风险；
- 院系管理员关注批量业务和异常；
- 业务部门关注全局进度和规则配置；
- 领导关注指标、异常和管理判断。

角色差异应体现在工作台、任务优先级和操作入口，而不仅是菜单权限。

---

## 3.3 任务驱动：事找人

优先形成：

```text
业务事件
→ 产生待办/任务
→ 用户直接办理
→ 状态变化
→ 触发下一任务
```

消息、待办、流程不要各自成为孤立体系。

---

## 3.4 默认简单，复杂按需展开

复杂B端系统不能通过“隐藏所有功能”追求极简。

正确方向：

```text
默认路径简单
+
高级设置按需展开
```

标准客户应尽量开箱即用，复杂客户才进入高级配置。

---

## 3.5 数据必须能继续行动

不要把“数据驱动”理解成增加看板。

例如：

```text
未提交成绩 32门
```

应继续支持：

```text
查看涉及课程
→ 定位教师
→ 批量提醒
→ 跟踪处理结果
```

形成：

```text
发现
→ 定位
→ 判断
→ 行动
→ 反馈
```

---

## 3.6 AI嵌入业务，不只做聊天入口

AI可以承担：

- 找功能
- 找信息
- 预填
- 校验
- 总结
- 推荐
- 异常提示
- 方案辅助

高影响业务动作应优先：

```text
AI建议
+ 原因
+ 影响范围
+ 人工确认
```

不要默认自动替用户做高责任决策。

---

# 4. 先做角色任务地图

对每个主要角色建立：

| 角色 | 高频任务 | 周期性任务 | 异常任务 | 关注数据 | 主要协作对象 |
|---|---|---|---|---|---|

任务优先级可考虑：

- 频率
- 时效
- 风险
- 操作成本
- 业务价值

工作台不是功能收藏夹，而是角色当前工作的组织方式。

---

# 5. 工作台设计

一个角色工作台优先考虑：

```text
当前最重要任务
即将截止事项
异常/风险
业务进度
常用入口
数据概览
```

不要把所有模块入口都做成同权重宫格。

参考：

`references/workbench-and-task-patterns.md`

---

# 6. 多身份设计

目标：减少频繁切换身份，但不能消除责任边界。

推荐原则：

```text
账号统一
任务整合
场景分组
责任身份可感知
数据权限仍隔离
```

例如一个用户同时是：

```text
教师 + 导师 + 评审专家 + 学院管理员
```

可以统一展示待办，但在执行高责任操作时应明确：

> 当前以“学院管理员”职责处理。

“无需切换用户组”不等于“所有身份混成一个权限”。

---

# 7. 信息架构

IA优先从：

```text
角色任务
+ 业务对象
+ 生命周期
+ 使用频率
```

推导，而不是复制旧菜单。

建议区分：

### 工作入口

待办、任务、常用场景。

### 业务管理

围绕核心业务对象和流程。

### 数据与分析

监控、异常、画像、报告。

### 规则与配置

低频管理操作，不应和日常业务同层竞争注意力。

---

# 8. 菜单原则

避免：

- 多层菜单嵌套；
- 同一个业务对象散落在很多不相关菜单；
- 用历史组织结构代替用户心智；
- 高频任务藏在配置模块里。

优先：

- 2层左右可理解导航；
- 场景入口与对象管理并存；
- 通过页面内筛选/视图切换解决合理维度差异；
- 低频配置与高频业务分离。

---

# 9. 页面结构

每个页面先定义：

```text
页面目的
主要角色
主要业务对象
所处流程阶段
主任务
次任务
关键状态
```

再设计：

- 信息区域
- 主操作
- 次操作
- 批量操作
- 筛选条件
- 状态反馈
- 异常提示

不要先决定“左边表格右边详情”再找业务来填。

---

# 10. 主操作原则

一个页面应尽量让用户知道：

> 现在最应该做什么。

区分：

- 主操作
- 次操作
- 危险操作
- 高级操作

高频场景优先减少：

- 页面跳转
- 重复筛选
- 重复选择对象
- 重复输入已有数据
- 不必要确认弹窗

---

# 11. 批量操作

管理端尤其检查：

- 批量选择
- 批量审核
- 批量提醒
- 批量导入/导出
- 批量调整
- 批量异常处理

批量动作必须说明：

- 作用范围
- 不满足条件的对象如何处理
- 部分成功怎么办
- 是否可撤销
- 是否需要结果报告

---

# 12. 流程可视化

对长流程业务优先展示：

- 当前阶段
- 已完成阶段
- 下一阶段
- 当前责任人/角色
- 关键截止时间
- 阻塞原因

不要只显示“状态=审核中”。

用户更关心：

> 现在卡在哪里、谁处理、下一步是什么。

---

# 13. 配置端体验

配置端设计目标不是“把所有参数摆出来”。

优先：

```text
推荐模板
→ 核心配置
→ 高级配置
→ 影响预览
→ 校验
→ 发布/生效
```

复杂规则建议提供：

- 默认值
- 模板
- 条件显示
- 冲突校验
- 生效范围说明
- 修改影响提示

---

# 14. 自然语言入口

自然语言适合：

### 快速找服务

“我要查成绩”

### 业务咨询

“延期申请需要什么材料？”

### 查询分析

“哪些学院还有成绩没提交？”

### 辅助办理

“帮我准备请假申请”

但复杂正式业务最好在生成结果后进入结构化确认，而不是完全留在聊天里完成。

---

# 15. 体验评审维度

每个重点场景至少评估：

| 维度 | 问题 |
|---|---|
| 找到 | 用户能快速找到入口吗？ |
| 理解 | 知道当前发生什么吗？ |
| 判断 | 关键规则和原因清楚吗？ |
| 操作 | 高频路径是否足够短？ |
| 批量 | 管理端能高效处理吗？ |
| 异常 | 失败/驳回后知道怎么办吗？ |
| 反馈 | 操作结果和下一步清楚吗？ |
| 数据 | 能从数字继续定位和行动吗？ |
| AI | AI是否减少实际工作量？ |

详细检查参考：

`references/b2b-ux-checklist.md`

# 17. 不做什么

本 Skill 不应：

- 静默改变TO-BE业务规则；
- 为了页面简单删除复杂但真实的业务场景；
- 把所有能力都塞进首页；
- 把AI当作所有交互的替代；
- 只做视觉风格升级。

如果发现业务模型不合理，应提交给 Leader/TO-BE Agent 重新决策。

---

# 18. 完成标准

完成后应能回答：

1. 每类角色打开系统最先看到什么？
2. 高频任务是否可以快速完成？
3. 长流程业务是否能看懂当前位置和下一步？
4. 多身份是否减少切换但责任仍清晰？
5. 管理端批量处理是否高效？
6. 数据是否能驱动行动？
7. 配置复杂度是否被合理收敛？
8. AI是否真正减少寻找、录入、判断或整理成本？

如果只是“新版页面更漂亮”，说明还没有完成产品体验重构。
