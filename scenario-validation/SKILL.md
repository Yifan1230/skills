# Scenario Validation

## 1. 目标

验证 TO-BE 是否真正覆盖目标业务，而不是只验证页面、接口或字段是否正常。

核心问题：

> **旧系统的重要业务场景在新系统里去了哪里？新业务规则在真实角色、状态、配置和异常情况下是否闭环？**

---

# 2. 输入契约

优先使用：

- AS-IS业务场景；
- AS-IS业务规则；
- TO-BE业务场景；
- TO-BE业务规则；
- 生命周期；
- 角色权限；
- 配置模型；
- AS-IS/TO-BE业务映射；
- 迁移策略；
- Decision Log。

如果输入验收条件只有“字段变成某值、表新增记录、接口返回200”，先要求补充对应业务结果。

---

# 3. 业务验收与技术验证分层

## 3.1 产品业务验收

默认主输出，使用：

```text
角色
业务对象
当前业务状态
业务配置
用户动作
预期业务结果
下一状态
后续任务
```

## 3.2 技术验证附录

可以包含：

- 字段值；
- 表记录；
- 接口返回；
- 日志；
- 消息队列；
- 技术脚本结果。

但不能用技术验证替代业务验收。

---

# 4. 旧场景不能无声消失

每个重要AS-IS场景必须有明确去向：

```text
保留
优化后保留
合并
转换为配置
转换为新场景
有意废弃
待确认
缺失
```

“有意废弃”必须有Decision Log。

“缺失”是问题，不能为了通过验收改名为“优化”。

---

# 5. 场景兼容矩阵

| AS-IS业务场景 | TO-BE业务场景 | 处理方式 | 业务差异 | 是否接受 | 决策依据 |
|---|---|---|---|---|---|

优先覆盖：

- 高频；
- 高风险；
- 高价值；
- 高定制频率；
- 历史客户依赖。

不要只对比页面名、接口名或功能按钮名。

---

# 6. 业务规则覆盖

对关键规则确认：

- 正常条件下是否生效；
- 不满足条件时是否正确阻止；
- 不同角色是否正确；
- 不同业务状态是否正确；
- 不同配置是否正确；
- 异常后是否能继续；
- 边界条件是否明确。

| 业务规则 | 正向场景 | 禁止场景 | 异常场景 | 配置差异 | 状态 |
|---|---|---|---|---|---|

规则名称必须是业务表达，不使用内部校验方法名。

---

# 7. 场景分类

至少覆盖：

## 主流程
正常发起、处理、完成。

## 重要分支
不同类型、规则、配置产生的业务路径。

## 状态边界
不同状态下是否允许修改、撤回、审核、恢复等。

## 权限与数据范围
本人、本学院、全校、指定对象、管理员等。

## 异常恢复
驳回后重提、撤回后修改、停开后恢复、超时、部分失败、外部失败等。

## 配置差异
只覆盖真实允许的关键组合。

## 迁移场景
历史已完成、草稿、审核中、评审中、旧权限映射等。

---

# 8. 业务验收用例

编号：

```text
AC-001
AC-002
...
```

每条至少包含：

| 项目 | 内容 |
|---|---|
| 对应场景 | |
| 对应规则 | |
| 角色 | |
| 业务对象 | |
| 前置业务状态 | |
| 业务配置 | |
| 操作 | |
| 预期业务结果 | |
| 预期下一状态 | |
| 后续任务/通知 | |
| 风险级别 | |

正确：

> 申请人撤回审核中的申请后，申请重新进入可编辑状态，原审核任务关闭。

不够：

> status从2改成0，审核表记录失效。

后者只能进入技术验证附录。

---

# 9. 正向 + 反向验证

关键规则至少验证：

```text
应该允许
+
应该禁止
```

例如：

### 正向
待学院审核 + 学院审核人 + 本学院数据 → 可以审核。

### 反向
已完成 + 学院审核人 → 不允许再次审核。

不要用“接口返回403”作为主验收描述；应先说明业务上为什么不允许。

---

# 10. 生命周期覆盖

对每个核心对象检查：

- 每个业务状态是否有进入场景；
- 非终态是否有合理离开路径；
- 终态是否被错误操作；
- 逆向路径是否覆盖；
- 是否存在无法解释的状态。

正文使用业务状态名称。

技术状态码只允许在附录映射。

---

# 11. 决策表覆盖

检查：

- 每个合法业务分支是否有场景；
- 非法组合是否被阻止；
- 默认业务行为是否明确；
- 未配置时系统做什么；
- 配置变化是否只影响预期范围。

不要机械穷举笛卡尔积。

---

# 12. 数据到行动闭环

如果TO-BE包含监控、预警、画像或驾驶舱，验收链路应覆盖：

```text
发现问题
→ 定位业务对象
→ 找到责任人
→ 发起处理
→ 处理结果回写
```

不能只验收“数字显示正确”。

---

# 13. AI场景验收

至少验证：

- AI是否正确理解业务意图；
- 推荐是否有依据；
- 不确定性是否说明；
- 是否越权；
- 高责任动作是否人工确认；
- AI失败时是否可回到正常业务路径；
- AI建议是否影响正式业务数据，如何留痕。

AI体验不能替代正式业务规则。

---

# 14. 迁移验收

迁移验收先看业务连续性：

正确：

> 原处于专家评审中的项目迁移后，原专家仍能继续完成未结束评审，已提交结果不丢失。

技术附录再验证：

- 数量；
- 字段；
- 表关系；
- 接口；
- 日志。

不要把“数据条数一致”当作迁移业务成功。

---

# 15. 风险优先级

```text
P0 核心业务阻断 / 数据责任 / 权限安全
P1 关键主流程和高频异常
P2 常用配置和一般分支
P3 低频边缘场景
```

覆盖率高不代表风险低。

---

# 16. 回归范围

从业务链路生成回归范围：

```text
业务规则
→ 业务状态
→ 业务场景
→ 角色
→ 页面/任务
→ 报表/集成
→ 迁移逻辑
```

而不是“改了哪个页面就测哪个页面”。

---

# 17. Product Readability Gate

提交前检查：

- 主验收用例是否都在描述业务结果？
- 是否出现字段名、表名、方法名、状态码替代业务含义？
- 用户/产品经理能否不看源码判断“通过还是失败”？
- 技术验证是否被隔离到附录？
- 每个失败是否能说明业务后果？

不满足则验收文档不通过。

# 19. 不做什么

本 Skill 不应：

- 静默修正TO-BE；
- 用页面测试替代业务场景；
- 用字段值替代业务结果；
- 只验证正常路径；
- 为覆盖率机械生成无意义组合；
- 把缺失能力伪装成废弃。

---

# 20. 完成标准

完成后应能回答：

1. 旧系统重要业务场景在新系统去了哪里？
2. 新规则是否有正向和反向验证？
3. 状态、权限、配置分支是否覆盖？
4. 异常后业务是否能继续？
5. 在途和历史迁移是否通过业务验证？
6. 哪些是有意废弃，哪些是真缺失？
7. 哪些风险阻断上线？
8. 产品经理是否可以完全脱离字段、表和接口判断验收结果？

如果只能回答“页面正常、接口成功、字段正确”，产品级验收尚未完成。
