# Scenario Validation

## 1. 目标

验证 TO-BE 是否真正覆盖目标业务，而不是只验证页面是否能打开。

核心问题：

> **旧系统的重要业务场景在新系统里去了哪里？新设计的规则在各种真实情况和边界条件下是否能闭环？**

本 Skill 重点输出：

- AS-IS / TO-BE场景兼容矩阵
- 业务规则覆盖矩阵
- 主流程、分支、异常、边界场景
- 迁移/升级场景
- 业务验收用例
- 回归范围
- 未覆盖和待确认项

---

## 2. 输入前提

优先输入：

- AS-IS业务场景库
- AS-IS业务规则
- TO-BE业务场景库
- TO-BE业务规则
- 生命周期
- 角色权限
- 配置模型
- AS-IS→TO-BE映射
- 迁移策略
- Decision Log

如果TO-BE业务模型尚未稳定，本阶段可以做早期场景走查，但不要输出“最终通过”。

---

# 3. 第一原则：旧场景不能无声消失

每个重要AS-IS场景都必须有一个明确结论：

```text
保留
优化后保留
合并
转换为配置
转换为新场景
有意废弃
待确认
缺失
```

其中：

- “有意废弃”必须有明确决策依据；
- “缺失”属于问题，不应自动解释为产品优化；
- “待确认”必须进入阻塞/风险清单。

---

# 4. 建立场景兼容矩阵

输出：

| AS-IS场景 | TO-BE场景 | 处理方式 | 业务差异 | 是否接受 | 决策/证据 |
|---|---|---|---|---|---|

优先覆盖：

- 高频场景
- 高风险场景
- 高价值场景
- 高定制频率场景
- 历史客户依赖场景

不要只对比功能名称。

---

# 5. 业务规则覆盖

对每条关键业务规则，至少确认：

- 正常条件下是否生效；
- 不满足条件时是否正确阻止；
- 角色不同是否符合预期；
- 状态不同是否符合预期；
- 配置不同是否符合预期；
- 边界值是否明确；
- 异常后是否能够恢复/继续。

输出：

| 规则 | 覆盖场景 | 正向 | 反向/禁止 | 异常 | 边界 | 状态 |
|---|---|---|---|---|---|---|

详细参考：

`references/coverage-model.md`

---

# 6. 场景分类

业务验收至少从以下几类建立场景。

## 6.1 主流程

正常发起、处理、完成。

## 6.2 分支

不同业务类型、配置、处理方式产生的路径。

## 6.3 状态边界

不同状态下：

- 是否允许操作；
- 是否允许修改；
- 是否允许撤回；
- 是否可以重复执行。

## 6.4 权限和数据范围

例如：

- 本人
- 本学院
- 全校
- 指定专家
- 管理员

必须同时检查“应该能看到”和“不应该看到”。

## 6.5 异常恢复

例如：

- 驳回后重提
- 撤回后修改
- 超时
- 部分失败
- 数据不完整
- 外部系统失败

## 6.6 配置差异

只覆盖产品实际允许的关键组合，不机械穷举所有组合。

## 6.7 迁移场景

例如：

- 历史已完成数据
- 草稿迁移
- 审核中迁移
- 评审中继续旧流程
- 老权限映射

# 7. 业务验收用例

验收用例编号：

```text
AC-001
AC-002
...
```

每条至少包含：

| 项目 | 内容 |
|---|---|
| 用例编号 | AC-xxx |
| 对应场景 | |
| 对应规则 | |
| 角色 | |
| 前置数据/状态 | |
| 配置 | |
| 操作 | |
| 预期业务结果 | |
| 预期状态变化 | |
| 后续任务/通知 | |
| 风险级别 | |

不要把“按钮点击成功”作为业务验收结果。

详细模板参考：

`references/acceptance-case.md`

---

# 8. 正向 + 反向验证

关键规则至少设计一对：

```text
应该允许
+
应该禁止
```

例如：

### 正向

待审核 + 学院审核人 + 本学院数据 → 可以审核。

### 反向

已完成 + 学院审核人 → 不允许再次审核。

只验证正向路径很容易漏权限和状态问题。

---

# 9. 状态机覆盖

对每个核心对象检查：

- 每个状态是否至少有一个进入场景；
- 非终态是否有合理离开路径；
- 终态是否被错误操作；
- 逆向路径是否覆盖；
- 是否存在无入口状态；
- 是否存在无法离开的状态。

如果TO-BE定义了状态但没有业务场景，标记设计缺口。

---

# 10. 决策表覆盖

对多条件决策表检查：

- 每个合法分支是否至少一个场景；
- 非法组合是否被阻止；
- 默认分支是否明确；
- 未配置时系统行为是否明确；
- 配置变化是否只影响预期范围。

不要机械覆盖理论上的所有笛卡尔积。

---

# 11. 数据到行动闭环

如果TO-BE包含监控、预警、画像或驾驶舱，验收不止看数字。

检查：

```text
发现问题
→ 定位对象
→ 发起处理
→ 责任人办理
→ 处理结果回写
```

例如：

“未提交成绩32门”应验证是否能够继续定位课程和提醒教师。

---

# 12. AI场景验收

AI辅助业务至少验证：

- 输入理解是否正确；
- 推荐是否有依据；
- 是否说明不确定性；
- 是否会越权读取/操作；
- 高责任动作是否要求确认；
- AI失败时是否能回到传统业务路径；
- AI建议是否改变正式业务数据，如何留痕。

AI体验不能替代正式业务规则验收。

---

# 13. 迁移验收

迁移用例重点验证业务一致性，而不是只验证数据条数。

至少检查：

- 数量一致性
- 关键字段
- 状态映射
- 对象关系
- 权限
- 在途任务
- 报表结果
- 外部接口

例如：

> 原“评审中”项目迁移后，原专家仍能看到自己的评审任务，并且已经提交的评分不丢失。

---

# 14. 风险驱动优先级

验收优先级建议：

```text
P0 阻断核心业务/数据责任/权限安全
P1 关键主流程和高频异常
P2 常用配置和一般业务分支
P3 低频边缘场景
```

不要平均分配验证资源。

---

# 15. 回归范围生成

当一个业务规则或对象变化时，沿以下链路生成回归范围：

```text
业务规则
→ 关联状态
→ 关联场景
→ 关联角色
→ 关联页面/任务
→ 关联接口/报表
→ 关联迁移逻辑
```

这比“改了哪个页面就测哪个页面”更可靠。

---

# 16. 缺失与有意废弃

### 缺失

AS-IS存在且仍有业务价值，但TO-BE没有对应处理。

必须反馈Leader/TO-BE Agent。

### 有意废弃

必须至少有：

- Decision Log；
- 影响客户/用户；
- 替代方案或退出策略；
- 是否需要兼容期。

不要把缺失写成废弃来通过验收。

---

# 17. 覆盖报告

最终输出建议：

| 类型 | 总数 | 已覆盖 | 缺失 | 待确认 | 覆盖率 |
|---|---:|---:|---:|---:|---:|
| AS-IS核心场景 | | | | | |
| TO-BE核心规则 | | | | | |
| 核心状态 | | | | | |
| 高风险异常 | | | | | |
| 权限边界 | | | | | |
| 迁移场景 | | | | | |

覆盖率不是唯一目标。

高风险场景未覆盖时，即使总覆盖率很高，也不应判定通过。

# 19. 不做什么

本 Skill 不应：

- 静默修正TO-BE设计；
- 用页面测试替代业务场景验证；
- 只验证正常路径；
- 为追求覆盖率机械生成大量无意义组合；
- 把旧系统所有行为都当成必须保留；
- 把没有明确决策的缺失能力标成“废弃”。

发现设计缺口时，反馈Leader重新决策。

---

# 20. 完成标准

完成后应能回答：

1. 旧系统重要场景在新系统里去了哪里？
2. 新业务规则是否有正向和反向验证？
3. 状态、权限、配置分支是否覆盖？
4. 异常后业务是否能继续闭环？
5. 在途和历史迁移是否通过业务验证？
6. 哪些场景是有意废弃，哪些是真正缺失？
7. 哪些风险仍会阻断上线？
8. 一个规则变化后应该回归哪些业务？

如果只能回答“页面测试通过”，说明产品级验收尚未完成。
