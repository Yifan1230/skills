# Product Readability Contract

本文件定义系统改版 Agent Suite 的统一输出契约。

## 1. 两层信息模型

### A. 技术事实层

可以包含：

- 字段名
- 表名
- 方法/函数名
- API内部名称
- 状态码
- SQL
- 调用关系
- 日志
- 技术算法

用途：证明系统实际上如何实现。

主要由“代码逆向工程”Agent维护。

### B. 产品业务层

必须包含：

- 业务目的
- 角色
- 业务对象
- 业务状态
- 业务动作
- 业务规则
- 业务场景
- 业务结果
- 异常与恢复

用途：产品理解、产品抽象、TO-BE设计、UX、迁移决策和业务验收。

---

## 2. 技术信息不得污染产品正文

产品正文默认禁止出现：

```text
SFXS
ZT=99
T_XXX
validateCanEdit()
doAzpy()
copyForHbpk
A<>B
字段A=1
```

如果这些内容必须保留，只能放：

```text
技术证据
证据附录
evidence/
technical-mapping/
technical-validation/
```

---

## 3. 业务翻译的最低要求

任何从代码发现的重要能力，在进入产品业务层之前必须回答：

1. 这个能力在业务上解决什么问题？
2. 谁使用？
3. 处理哪个业务对象？
4. 在什么业务条件下发生？
5. 用户执行什么业务动作？
6. 系统产生什么业务结果？
7. 有什么异常、限制、恢复或后续动作？

无法回答时标记【待确认】，不要用技术过程替代业务含义。

---

## 4. 禁止代码式流程图

不合格：

```text
选周次 → newzcbh → doAzpy → 写T_XXX
```

合格：

```text
选择需要调整的教学周
→ 系统计算受影响课程
→ 用户预览调整结果
→ 确认执行
→ 更新课程安排并保留调整记录
```

---

## 5. 各阶段的阅读层级

### 代码逆向

主要工作在技术事实层。

### 逆向业务模型

必须完成技术事实 → 业务语义翻译。

### 定制差异

主结论应为业务差异；技术差异只作为证据。

### 产品抽象

只使用业务能力和业务差异做分类。

### TO-BE

只使用业务概念定义目标模型。

### UX/IA

页面和交互命名来自业务语言。

### 迁移

主报告先讲业务迁移；字段/接口映射下沉技术附录。

### 验收

主用例先验业务结果；字段/接口/表记录属于技术验证。

---

## 6. Leader Gate

任何面向产品的阶段产物，如果出现以下情况，应直接退回：

- 不看源码无法理解；
- 业务状态仍用数字或代码表示；
- 流程图是方法调用链；
- 功能说明只是字段变化的中文改写；
- 产品能力直接使用技术模块名；
- 验收结果只有字段值或接口成功；
- 迁移报告只有字段映射和脚本。

最终判断：

> **事实正确只是底线；业务含义清晰、能直接用于产品决策，才算合格。**
