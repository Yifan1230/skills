# 子 Agent 调度规范

## 1. 任务下发模板

Leader下发子任务时，尽量包含：

```text
任务目标：
分析范围：
输入材料：
已有结论：
必须回答的问题：
禁止越界事项：
输出文件：
验收标准：
```

---

## 2. 什么时候调用哪个 Agent

### 代码逆向工程

适合：
- 某个状态、按钮、权限、配置的真实实现不清楚；
- 需要找出隐藏条件；
- 业务逆向结果缺少代码证据。

不要让它决定TO-BE方案。

### 逆向业务模型

适合：
- 需要建立AS-IS对象、状态、规则、场景；
- 页面很多但业务主线不清；
- 需要跨页面还原完整业务过程。

不要让它直接覆盖现有事实做重构。

### 定制应用分析

适合：
- 有多个客户版本；
- 想判断哪些差异反复出现；
- 想区分标品缺陷和客户特例。

### 产品能力抽象

适合：
- 已经知道现状和定制差异；
- 需要决定哪些进入标准、配置、组合、扩展或定制。

如果AS-IS仍不清楚，不要调用它替代现状分析。

### TO-BE业务设计

适合：
- 产品边界已经基本确认；
- 需要重新设计对象、生命周期、流程和规则。

### UX/IA设计

适合：
- TO-BE业务模型相对稳定；
- 需要设计工作台、导航、页面和交互路径。

### 影响与迁移

适合：
- TO-BE已经形成；
- 需要判断老数据、老配置、在途流程如何升级。

### 场景验收

适合：
- TO-BE和迁移方案基本形成；
- 需要检查是否漏场景、生成验收和回归范围。

---

## 3. 最小调度原则

不要因为拥有很多Agent，就机械全调。

例如：

> 只想确认一个旧按钮为什么不显示

优先调用代码逆向，不需要完整跑产品抽象和TO-BE。

> 要重构整个专家评审模块

通常需要：

```text
业务逆向
+ 定制分析（若有多个客户）
→ 产品抽象
→ TO-BE设计
→ UX
→ 迁移
→ 场景验收
```

---

## 4. 子 Agent 不得自行改变上游事实

如果下游 Agent 发现上游结论可能有问题：

```text
提出冲突
→ 说明原因
→ 请求Leader回派补证据
```

不要直接在下游文档里静默修改AS-IS。
