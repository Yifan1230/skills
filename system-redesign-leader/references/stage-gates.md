# System Redesign Stage Gates

## Gate 1A — 产品可读性

AS-IS进入产品分析前，必须先通过可读性检查。

### 必须满足

- [ ] 产品正文不依赖阅读源码才能理解
- [ ] 业务状态使用业务名称，不使用状态数字
- [ ] 流程使用业务动作，不使用方法调用链
- [ ] 业务规则描述“业务条件和结果”，不是字段判断的中文改写
- [ ] 字段、表、方法、接口、SQL等技术细节已下沉证据层
- [ ] 每项重要功能都解释了业务目的、角色、对象、条件和结果

### 自动失败信号

产品正文出现：

```text
T_XXX
字段A=1
ZT=99
xxx()
A<>B
内部接口编码
```

且不在“技术证据/附录”中。

## Gate 1B — AS-IS业务模型完整度

### 必须满足

- [ ] 核心业务对象已识别
- [ ] 对象关系清楚
- [ ] 主要生命周期已解释
- [ ] 关键业务规则和决策分支已业务化
- [ ] 主流程和关键异常流程已覆盖
- [ ] 角色、责任和数据范围清楚
- [ ] 重要配置已识别
- [ ] 待确认问题已单列
- [ ] 技术上发现但尚未翻译成业务含义的内容不计入“已完成”

不通过时优先回到业务逆向，不进入产品抽象。

---

## Gate 2 — 产品边界稳定度

### 必须满足

- [ ] 核心能力使用业务概念命名
- [ ] 主要客户差异已经归类为参数/规则/流程/权限/配置等业务差异
- [ ] 标准/配置/组合/扩展/定制/废弃策略明确
- [ ] 没有把所有差异都做成配置
- [ ] 配置作用层级和默认策略明确
- [ ] 高争议能力有Decision Log

如果能力地图仍然以旧页面、字段、接口或代码模块为中心，不通过。

---

## Gate 3 — TO-BE达到研发输入条件

### 业务模型

- [ ] 目标业务对象稳定
- [ ] 生命周期稳定
- [ ] 主流程和异常流程闭环
- [ ] 主要业务规则和决策表明确
- [ ] 角色责任和权限边界明确
- [ ] 配置归属明确

### 产品体验

- [ ] 页面/工作台可追溯到业务场景
- [ ] 页面、按钮、状态、提示语使用业务语言
- [ ] 高频任务路径清楚
- [ ] 异常情况下用户知道为什么不能做、下一步怎么办

### 文档

- [ ] 产品文档可脱离源码独立评审
- [ ] 技术约束已与业务设计分层
- [ ] 高风险待确认项已处理或明确接受风险

只有高保真页面，不通过。

---

## Gate 4 — 发布/实施准备度

### 必须满足

- [ ] AS-IS核心场景在TO-BE中有明确去向
- [ ] 重要规则可追溯
- [ ] 历史和在途业务迁移策略明确
- [ ] 角色/权限迁移明确
- [ ] 客户和用户切换影响明确
- [ ] 有意废弃内容有Decision Log
- [ ] 高风险业务场景有验收用例
- [ ] 产品验收使用业务结果表达
- [ ] 技术验证独立存在，不替代业务验收
- [ ] 剩余待确认项不阻断上线

---

# Gate 判断原则

Gate不是检查“文档有没有写”，而是检查：

> **下一个阶段能否在不重新解释上游材料的情况下直接工作。**

如果下游仍需要问“这个字段是什么意思”“这个方法到底代表什么业务”，说明上游 Gate 不应通过。
