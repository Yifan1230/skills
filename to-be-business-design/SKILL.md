# TO-BE Business Design

## 1. 目标

把已确认的现状问题和产品能力边界，转换成一套可落地、可解释、可继续做UX和研发需求的目标业务模型。

本 Skill 回答：

- 新系统应该有哪些业务对象？
- 对象之间如何关联？
- 生命周期如何设计？
- 哪些规则固定，哪些允许配置？
- 不同角色如何协作？
- 正常、异常、特殊场景如何闭环？
- 旧系统重要能力在新模型里去了哪里？

不要从页面或技术结构开始设计。

---

# 2. 输入契约

优先使用：

- AS-IS业务对象模型；
- 生命周期；
- 业务规则与场景；
- 定制差异；
- 产品能力抽象结果；
- 改版目标；
- Decision Log。

输入中如果仍大量出现字段名、表名、方法名、状态码，先要求上游完成业务语义翻译。

TO-BE设计不应直接消费技术调用链作为业务模型基础。

---

# 3. 产品语言规则

目标模型中的名称必须来自业务语义，例如：

```text
教学任务
排课安排
合班关系
停开
恢复
审核中
已确认
```

不要把：

```text
SFXS
ZT=99
copyForHbpk
ReviewService
T_XXX
```

带进目标业务模型。

如果存在技术约束，单独记录为：

```text
【实现约束/待研发评估】
```

而不是把技术名变成产品概念。

---

# 4. 强制顺序

```text
目标与约束
→ 目标业务对象
→ 对象关系
→ 生命周期
→ 业务规则
→ 角色协作
→ 配置边界
→ 业务场景
→ 端到端流程
→ AS-IS/TO-BE对照
```

页面和视觉设计交给UX/IA Agent。

---

# 5. 先定义目标问题

每个改版模块先说明：

- 现状业务问题是什么；
- 根因是什么；
- 本轮要解决什么；
- 暂不解决什么；
- 哪些业务约束不能改变；
- 哪些历史兼容需要保留。

不要因为代码结构复杂就等同于业务模型有问题。

---

# 6. 目标业务对象

每个目标对象至少说明：

| 项目 | 内容 |
|---|---|
| 对象名称 | 业务人员可理解的名称 |
| 业务定义 | 它代表什么 |
| 产生方式 | 如何产生 |
| 上下级/关联对象 | 与谁存在稳定关系 |
| 主要状态 | 中文业务状态 |
| 主要业务动作 | 用户能做什么 |
| 责任角色 | 谁负责 |
| 与AS-IS差异 | 保留/拆分/合并/新增/废弃 |

对象设计要求：

- 业务含义单一；
- 生命周期可解释；
- 不依赖页面存在；
- 不因单客户特例污染核心模型；
- 不以数据库表一一对应为目标。

---

# 7. 生命周期设计

对核心对象设计完整业务生命周期。

至少考虑：

- 初始；
- 正向处理；
- 审核/确认；
- 驳回/退回；
- 撤回；
- 重提；
- 停开/恢复；
- 取消/终止；
- 暂停/恢复；
- 延期；
- 关闭/归档。

| 当前业务状态 | 业务动作 | 前置条件 | 角色 | 下一业务状态 | 业务后果 |
|---|---|---|---|---|---|

不要为了适配旧状态码而保留没有清晰业务含义的状态。

---

# 8. 业务规则设计

规则编号：

```text
TBR-001
TBR-002
...
```

每条规则说明：

- 适用对象；
- 业务条件；
- 允许/禁止动作；
- 结果；
- 例外；
- 配置依赖；
- 关联场景。

规则必须使用业务表达。

正确：
> 教学任务锁定后，普通维护人员不能继续修改排课安排。

错误：
> 当状态值为99时禁止调用编辑接口。

---

# 9. 配置与固定边界

根据产品抽象阶段结论明确：

- 哪些规则固定；
- 哪些配置；
- 配置属于哪个业务层级；
- 默认值；
- 是否允许下级覆盖；
- 修改配置是否影响在途业务。

配置名称必须表达业务含义，而不是技术参数名称。

---

# 10. 角色协作

| 角色 | 业务责任 | 处理对象 | 可执行动作 | 数据范围 | 进入条件 |
|---|---|---|---|---|---|

重点关注：

- 责任边界；
- 多角色接力；
- 多身份用户；
- 管理员强制能力；
- 数据范围变化。

---

# 11. 业务场景

场景编号：

```text
TSC-001
TSC-002
...
```

每个场景至少包含：

```text
场景目的
角色
业务对象
当前状态
前置条件
业务动作
业务结果
后续任务
异常/替代路径
```

必须覆盖：

- 主流程；
- 分支；
- 角色差异；
- 配置差异；
- 异常；
- 边界场景。

---

# 12. 端到端流程

流程图只允许出现业务动作和业务结果。

错误：

```text
A接口 → B方法 → C字段=1 → 写T_LOG
```

正确：

```text
提交申请
→ 学院审核
→ 审核通过
→ 根据评审规则决定是否进入专家评审
→ 确认结果
```

每个关键节点回答：

```text
谁
处理什么对象
为什么现在处理
处理后发生什么
下一责任人是谁
```

---

# 13. 业务事件与任务

建议识别：

### 业务事件

例如“申请已提交”“成绩逾期未提交”。

### 业务任务

例如“学院待审核”“教师待录成绩”。

优先形成：

```text
业务事件
→ 产生任务
→ 用户办理
→ 状态变化
→ 下一任务
```

为后续工作台和消息待办提供统一基础。

---

# 14. 与AS-IS对照

| AS-IS业务能力 | TO-BE业务能力 | 变化类型 | 变化原因 | 解决问题 | 影响 |
|---|---|---|---|---|---|

变化类型：

```text
保留
优化
拆分
合并
迁移
废弃
新增
```

不要用“字段A改成字段B”作为主要产品变化描述。

---

# 15. 产品可读性 Gate

提交前检查：

- 对象名称是否是业务概念？
- 状态是否是业务状态？
- 规则是否能被业务人员理解？
- 流程是否没有技术调用链？
- 是否把技术约束单独隔离？
- 产品经理不看源码能否评审这套TO-BE？

如果不能，重新设计表达，不进入UX阶段。

---

# 17. 不做什么

本 Skill 不负责：

- 高保真视觉；
- 前端技术方案；
- 数据库设计；
- 接口字段设计；
- 迁移脚本；
- 测试用例全集。

这些属于后续专业阶段。

---

# 18. 完成标准

完成后应能直接回答：

1. 新系统核心业务对象是什么？
2. 为什么这么拆？
3. 每个对象如何从产生到结束？
4. 谁在什么时候能做什么？
5. 哪些规则固定，哪些配置？
6. 主流程和异常流程是否闭环？
7. 旧系统重要业务去了哪里？
8. 产品经理是否可以完全脱离源码评审这套方案？

如果仍需要解释字段、表或方法才能看懂，TO-BE业务设计不合格。
