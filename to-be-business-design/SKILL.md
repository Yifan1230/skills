# TO-BE Business Design

## 1. 目标

把已经确认的现状问题和产品抽象结果，转换成一套可落地的目标业务模型。

本 Skill 重点回答：

- 新系统应该有哪些业务对象？
- 对象之间应该是什么关系？
- 生命周期如何设计？
- 哪些业务规则属于对象本身，哪些属于配置？
- 不同角色如何协作？
- 正常、异常、特殊场景如何运行？
- 哪些旧逻辑保留、合并、替换或废弃？

不要一开始画页面。

---

## 2. 输入前提

优先基于以下输入工作：

- AS-IS业务对象模型
- AS-IS生命周期
- AS-IS业务规则与场景
- 定制差异分析
- 产品能力抽象结果
- 已确认改版目标
- Decision Log

如果AS-IS核心事实仍不清楚，应退回补证据，而不是凭设计经验补齐。

---

# 3. 强制顺序

严格按照：

```text
目标与约束
→ 核心业务对象
→ 对象关系
→ 生命周期
→ 业务规则
→ 角色协作
→ 配置边界
→ 业务场景
→ 端到端流程
→ 与AS-IS对照
```

页面和视觉设计交给下游 UX/IA Agent。

---

# 4. 先定义目标问题

每个改版模块先明确：

- 现状根因是什么？
- 本轮设计要解决什么？
- 哪些问题暂不解决？
- 哪些行业/政策约束不能改变？
- 哪些历史兼容要求必须考虑？

避免“为了重构而重构”。

---

# 5. 目标业务对象

业务对象编号可沿用AS-IS并增加TO-BE标识，或建立映射。

每个目标对象至少说明：

| 项目 | 内容 |
|---|---|
| 对象名称 | |
| 业务定义 | |
| 产生方式 | |
| 上级/下级对象 | |
| 核心属性 | |
| 主要状态 | |
| 主要操作 | |
| 责任角色 | |
| 与AS-IS差异 | |

对象设计优先满足：

- 业务含义单一；
- 关系稳定；
- 生命周期可解释；
- 不依赖页面存在；
- 不因单客户特例污染核心模型。

判断对象拆分/合并参考：

`references/object-redesign.md`

---

# 6. 生命周期设计

对每个核心对象设计完整状态机。

至少覆盖：

- 初始状态
- 正向流转
- 审核/确认
- 驳回/退回
- 撤回
- 重新提交
- 取消/终止
- 暂停/恢复
- 延期
- 关闭/归档

输出：

| 当前状态 | 触发动作 | 前置条件 | 操作角色 | 下一状态 | 业务后果 |
|---|---|---|---|---|---|

状态设计要求：

- 每个状态有明确业务含义；
- 不为页面显示而造状态；
- 避免多个状态其实表达同一阶段；
- 避免用一个状态字段承担多个维度；
- 终态和可逆状态必须明确。

---

# 7. 业务规则设计

业务规则编号：

```text
TBR-001
TBR-002
...
```

每条规则说明：

- 规则名称
- 适用对象
- 前置条件
- 允许/禁止的动作
- 结果
- 例外
- 配置依赖
- 关联场景

优先把规则放在业务上，而不是放在页面按钮逻辑里。

---

# 8. 配置与固定边界

TO-BE不能简单复制所有旧配置。

使用产品抽象阶段的结论，明确：

- 哪些规则固定；
- 哪些允许配置；
- 配置属于哪个层级；
- 是否有默认值；
- 是否允许下级覆盖；
- 修改配置是否影响在途业务。

如果某个配置会产生大量非法组合，应限制组合或改为模板。

---

# 9. 角色协作模型

不要只写角色名称。

每个关键角色至少说明：

| 角色 | 责任 | 处理对象 | 可执行动作 | 数据范围 | 进入条件 |
|---|---|---|---|---|---|

重点关注：

- 责任边界；
- 多角色接力；
- 多身份用户；
- 管理员是否具有特殊强制能力；
- 角色变化是否影响数据范围。

---

# 10. 业务场景设计

场景编号：

```text
TSC-001
TSC-002
...
```

每个场景至少包含：

```text
角色
+ 业务对象
+ 当前状态
+ 前置条件
+ 操作
+ 业务结果
+ 后续任务
```

必须覆盖：

- 主流程
- 分支场景
- 角色差异
- 配置差异
- 异常场景
- 边界场景

不要机械穷举所有组合，只保留合理可达场景。

场景检查参考：

`references/scenario-design-checklist.md`

---

# 11. 端到端业务流程

跨对象、跨角色串起完整业务。

每个关键节点都应能回答：

```text
谁
处理什么对象
为什么现在处理
处理后产生什么状态/任务
下一责任人是谁
```

建议分开表达：

- 主流程
- 异常流程
- 特殊流程

流程图不是目标，业务闭环才是目标。

---

# 12. 任务与事件

复杂B端系统建议同时识别：

### 业务事件

例如：

- 申请已提交
- 审核已通过
- 成绩未按时提交
- 评审任务已分配

### 业务任务

例如：

- 学院管理员待审核
- 教师待录成绩
- 专家待评审

设计时尽量形成：

```text
业务事件
→ 产生任务
→ 用户办理
→ 状态变化
```

这为后续工作台、待办和消息设计提供统一基础。

---

# 13. 与AS-IS对照

每项重大TO-BE变化必须说明：

| AS-IS | TO-BE | 变化原因 | 解决问题 | 潜在影响 |
|---|---|---|---|---|

变化类型可以标记：

```text
保留
优化
拆分
合并
迁移
废弃
新增
```

不要让重大结构变化只存在于新流程图中而没有解释。

---

# 14. 设计判断标准

优先检查：

### 是否解决根因

如果现状问题是“规则层和执行层混在一起”，TO-BE应真正拆开，而不是换页面布局。

### 是否符合稳定性

长期稳定规则放上层，执行期变化放下层。

### 是否默认简单

标准场景应开箱即用，复杂场景按需展开。

### 是否避免组合爆炸

配置越多，不代表越好。

### 是否支持异常流程

正常路径好用但异常路径断裂，不算完整设计。

# 16. 不做什么

本 Skill 不负责：

- 详细视觉样式；
- 页面高保真；
- 前端技术方案；
- 数据迁移实施细节；
- 测试用例全集。

这些交给对应下游 Agent。

---

# 17. 完成标准

完成后应能回答：

1. 新系统核心对象是什么？
2. 为什么这么拆？
3. 每个对象如何从产生到结束？
4. 谁在什么时候能做什么？
5. 哪些规则固定，哪些配置？
6. 主流程和异常流程是否都闭环？
7. 旧系统的重要能力在新系统里去了哪里？
8. 新模型是否减少了历史耦合，而不是把复杂度换个位置？

如果这些问题不能回答，不进入UX页面设计。
